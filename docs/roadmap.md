[`.specify/memory/constitution.md`](../.specify/memory/constitution.md)。

## M6 测量单元 KPI 与动态口径

状态：已完成。

目标：

- 任务包里的 KPI 列按测量单元归属，目录未覆盖的指标自动入库，避免一次性全量配置。
- 业务口径（阈值、派生指标、绑定）在前台维护，不入代码和离线文件。

范围：

- 测量单元 KPI 模型（v5）：测量单元、指标资源、绑定与派生指标由 SQLite 权威维护，
  在线入口为 `/api/v5/kpi/measurement-units`、`/api/v5/kpi/measurement-resources`、
  `/api/v5/kpi/measurement-bindings` 与 `/api/v5/kpi/measurement-derived`。
- 任务执行时按 CSV 表头归属指标：复用既有指标、暴露跨测量单元冲突、自动入库新列（默认启用）。
- Git 基础资源 + SQLite 组合生成任务快照；快照不可变，单规则重跑优先复用。
- KPI 结果目录化（`metric_catalog`、`kpi_results`、`unclassified_metrics`）与单任务内趋势。
- 退役 `deploy/data/kpi/rules/*.json` 运行时依赖，不做历史迁移。

验收：

- 契约、lint、后端测试、前端构建和本地全流程通过。
- 空动态配置仍可生成合法任务快照。
- 配置变更后由用户手动重跑受影响规则。

## 后续演进

### 跨任务趋势分析

目标：

- 按任务元数据聚合历史任务。
- 支持不同时间、版本下的 KPI、资源、告警和话统趋势。

设计支撑：

- 任务元数据键跨任务稳定。
- `metrics[].value` 数值化。
- `metrics[].series[]` 支持趋势。
- `SystemInspection.version` 承载版本。

可能形态：

- 新增跨任务聚合服务。
- 新增趋势查询接口。
- 新增趋势展示组件。

### 数据层统一与刷新策略

状态：**已落地（034）**。

- SQLite 是界面展示数据的唯一来源：任务快照（含 `last_run_at` / `duration_ms` / 准备摘要）、规则结果（含隐藏规则）与 KPI 历史点长期保留。
- `output/` 与 `uploads/` 降级为执行期现场；`task.json` 仍作为可移植元数据快照保留，但界面不再以文件为准。
- 写入顺序：任务终态时先在单事务内发布 DB 快照（任务行 + 规则结果 + KPI 历史点 + 准备摘要），再写现场文件，最后执行留存清理。
- 刷新策略：前端轮询任务摘要（无活跃任务时停止）；列表、详情、规则结果、发现、指标与 KPI 趋势全部读 DB，现场缺失不降级、不空白。
- 本地 CLI（`build.py run`、单规则重跑）与在线 API 共用同一条发布路径，双模式结果一致。
- 升级路径：启动时对既有 `output/` 任务做幂等回填（任务行 + 规则结果 + KPI 历史点），回填完成前不执行留存清理。
- 仍不做：规则结果的版本历史（以最新一次执行为准）、执行日志与报告入库。

### 任务保留与磁盘治理

状态：**已落地（034）**；保留额度固定为 50，无配置入口。

- 保留集合 = 按 `COALESCE(last_run_at, created_at)` 倒序前 50 个任务 ∪ 全部 `pending` / `running` 任务（执行中豁免）。
- 清理范围：`uploads/<task_id>/`、`output/<task_id>/` 中不在保留集合内的任务目录，以及 `uploads/` 根目录中可派生已知 task_id 的散包；未消费散包与无法归属的目录不删除。
- 触发时机：每次任务终态发布完成后（完成/失败/重跑/重建/单规则重跑，含本地 CLI）；创建接口的兜底恢复写回现场不触发。
- 清理只删磁盘、不改 DB：现场清理后任务列表、详情、规则结果、发现与 KPI 趋势仍可查；报告与执行日志返回 410 `scene_cleaned`，重跑/重建返回 410 并提示重新上传同名数据包、确认覆盖后全量重建。
- 重传同名包先提示覆盖，确认后清空旧任务并全量重建（与 033 FR-024 对齐）；创建接口的同名 checksum 矩阵仅作探测未命中兜底（一致写回现场、不自动重跑；不一致 409 `package_checksum_conflict`）。
- 失败容错：单次删除失败只记录结构化日志，由下一次任务结束时的清理重试，不影响任务终态。
- 未采用：按时间天数过期、分层保留（只留结果删现场）、压缩归档、磁盘水位淘汰，以及"清理现场时同步删除 DB 记录"（DB 长期保留是本特性的目标）。

### 任务重建重跑

目标：

- 当指标配置、规则逻辑或巡检版本变化后，用户可以显式重建一个历史任务的输出结果，而不需要删除任务后重新上传同一个包。

可能方向：

- 新增独立的“重建重跑”操作，与普通重跑语义分开。
- 重建前清理并重建 `output/<task_id>/`，保留 `uploads/<task_id>/` 中的原始包。
- 重建时从当前配置生成新的 KPI 任务快照，再执行巡检。
- 执行前校验原始包仍然存在、任务不在执行中，并同步重置 DB 任务状态。
- 前端使用独立的确认入口和文案，避免用户误以为普通重跑会应用新配置。

约束：

- 继续保持“一个包 = 一个任务 = 一个输出目录”。
- 重建重跑是显式运维/重算动作，不得在普通重跑里隐式刷新历史快照。
- 涉及 API 时先更新 OpenAPI 契约，再实现接口和前端。


### 输入文件编码统一

目标：

- 为 CSV、日志和其他文本类输入建立统一的编码探测、解码和错误上报机制，避免各规则和工具重复实现编码兼容逻辑。

背景：

- 测量单元资源导入与任务 CSV 解析已通过共享解码工具支持 UTF-8 和 GB18030（含 GBK/GB2312）回退；其他规则和工具后续逐步收敛。
- 其他规则和工具后续也可能遇到编码不一致的历史文件，应先记录当前发生点和处理方式，再统一收敛。

可能方向：

- 建立共享文本输入解码服务，声明支持的编码、探测顺序和大小限制。
- 解析错误统一返回文件路径、行号、原始编码线索和可操作修复建议。
- 不尝试静默修复损坏字节；无法安全解码时保持 `skip` / `error` 语义。
- 在规则契约或任务日志中记录最终使用的编码和探测结果，便于追溯。
- 对二进制文件和文本文件先做稳定识别，避免误用文本解码。

约束：

- 不连接被检系统，也不修改原始上传包。
- 编码探测失败不得掩盖真实解析错误，也不得让单文件失败中断整个任务。
- 涉及规则结果契约时先更新数据模型和 OpenAPI，再实现规则或服务。
