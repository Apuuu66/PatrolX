## 后续演进

### 跨任务趋势分析

目标：

- 按任务元数据聚合历史任务。
- 支持不同时间、版本下的 KPI、资源、告警和话统趋势。

设计支撑：

- 任务元数据键跨任务稳定。
- `metrics[].value` 数值化。
- `metrics[].series[]` 支持趋势。
- `SystemInspection.version` 承载版本。

可能形态：

- 新增跨任务聚合服务。
- 新增趋势查询接口。
- 新增趋势展示组件。
- 契约如发生破坏性变更，升级 API 版本。

### 规则管理增强

可能方向：

- 规则运行历史查看。
- 规则执行耗时分析。
- 只读元数据管理增强。
- 后续再评估在线启停和参数配置。

### 字典管理增强

可能方向：

- 字典项编辑界面。
- 字典引用校验。
- 更完整的导入/导出能力。

### 部署与运行增强

可能方向：

- 生产部署配置模板。
- 备份/恢复策略。
- 大包处理性能优化。
- 队列与并发模型评估。

以上能力均不改变当前 Constitution 中的离线优先、契约驱动、规则隔离和轻量默认约束。

### 数据层统一与刷新策略

目标：

- 本地模式与在线模式统一写 DB，消除"output/ 唯一数据源"与 DB 双源并存的不一致。
- 明确 DB / output/ / task.json 的角色边界和写入顺序。

设计方向：

- DB 角色定位为任务索引 + 状态机，只存任务元数据，不存巡检结果。
- output/ 仍然是解压现场、规则结果和报告的存储位置。
- task.json 保留为可移植元数据快照，与 DB 冗余但保持同步。
- 写入顺序：先写 output/（工作产物），再更新 DB（索引）；DB 可从 output/ 重建。
- 刷新策略：前端保持轮询（无活跃任务时停止），API 读 DB 列表 + output/ 详情；本地模式写 DB 后 Web 轮询天然覆盖。
- 本地 `python main.py` 也写 DB（pending → running → completed），与在线模式生命周期一致。

当前差异：

- 在线模式创建到首次写 task.json 之间存在窗口期，只有 DB 知道任务存在。
- 本地模式（`main.py`）完全不写 DB，Web UI 只能看到 output/ 中的已完成任务。


### 任务保留与磁盘治理

目标：

- 任务数量增长后，控制 output/ 目录的磁盘占用，避免解压现场无限累积。

可能方向：

- **保留策略**：按时间（如 N 天）或任务数量（如最近 M 个）自动清理过期任务；可按任务元数据（版本、省份）配置例外。
- **分层保留**：任务完成后可选择只保留规则结果 JSON + report.html + task.json，删除解压现场和 prepared/ 中间数据（占大头）；保留完整现场的窗口期可配置。
- **归档**：过期任务压缩归档到独立目录或外部存储，需要时手动恢复到 output/。
- **磁盘水位**：设置磁盘占用上限或告警阈值，接近时提示清理或自动按策略淘汰最旧任务。
- **与 DB 联动**：清理 output/ 时同步删除或标记 DB 记录，避免出现"有索引无数据"的悬空任务。

约束：

- 不改变"一个包 = 一个任务 = 一个输出目录"的隔离模型。
- 清理和归档是运维操作，不是巡检流程的一部分；不在执行器中硬编码。
- 用户上传的原始包（uploads/）在任务完成且确认结果后可先行清理，释放空间。


### 任务重建重跑

目标：

- 当指标配置、规则逻辑或巡检版本变化后，用户可以显式重建一个历史任务的输出结果，而不需要删除任务后重新上传同一个包。

可能方向：

- 新增独立的“重建重跑”操作，与普通重跑语义分开。
- 重建前清理并重建 `output/<task_id>/`，保留 `uploads/<task_id>/` 中的原始包。
- 重建时从当前配置生成新的 KPI 任务快照，再执行巡检。
- 执行前校验原始包仍然存在、任务不在执行中，并同步重置 DB 任务状态。
- 前端使用独立的确认入口和文案，避免用户误以为普通重跑会应用新配置。

约束：

- 继续保持“一个包 = 一个任务 = 一个输出目录”。
- 重建重跑是显式运维/重算动作，不得在普通重跑里隐式刷新历史快照。
- 涉及 API 时先更新 OpenAPI 契约，再实现接口和前端。


### 输入文件编码统一

目标：

- 为 CSV、日志和其他文本类输入建立统一的编码探测、解码和错误上报机制，避免各规则和工具重复实现编码兼容逻辑。

背景：

- KPI 资源 CSV 离线导入已临时支持 UTF-8 和 GBK/GB2312/GB18030 回退，用于覆盖历史导出现场。
- 其他规则和工具后续也可能遇到编码不一致的历史文件，应先记录当前发生点和处理方式，再统一收敛。

可能方向：

- 建立共享文本输入解码服务，声明支持的编码、探测顺序和大小限制。
- 解析错误统一返回文件路径、行号、原始编码线索和可操作修复建议。
- 不尝试静默修复损坏字节；无法安全解码时保持 `skip` / `error` 语义。
- 在规则契约或任务日志中记录最终使用的编码和探测结果，便于追溯。
- 对二进制文件和文本文件先做稳定识别，避免误用文本解码。

约束：

- 不连接被检系统，也不修改原始上传包。
- 编码探测失败不得掩盖真实解析错误，也不得让单文件失败中断整个任务。
- 涉及规则结果契约时先更新数据模型和 OpenAPI，再实现规则或服务。
