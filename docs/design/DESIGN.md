# PatrolX Design System

PatrolX 是面向运维和巡检场景的桌面优先系统。UI 应该专业、克制、信息密度适中，并优先支持快速扫读和异常排查。

## Brand

- 产品名：PatrolX
- 页面标题：系统维护巡检平台
- 基调：可靠、清晰、工程化
- 避免营销页风格、大面积装饰、复杂动效

## Layout

- 桌面优先，目标宽度从 1280px 到 1920px。
- 主布局采用左侧固定导航 + 顶部栏 + 内容区。
- 内容区建议最大宽度不超过 1600px。
- 页面背景使用浅灰，内容使用白色卡片。
- 卡片之间保持 16px 到 20px 间距。
- 卡片内边距建议 16px 到 24px。

## Color

### Brand

- Primary：AntD 蓝，建议基于 `#1677ff`
- Page background：`#f5f5f5`
- Surface：`#ffffff`
- Border：`#f0f0f0`
- Text primary：`rgba(0, 0, 0, 0.88)`
- Text secondary：`rgba(0, 0, 0, 0.65)`
- Text tertiary：`rgba(0, 0, 0, 0.45)`

### Status

状态色必须全站一致：

| Status | 中文 | 颜色 |
| --- | --- | --- |
| pass | 通过 | 绿，基于 `#52c41a` |
| warn | 告警 | 黄，基于 `#faad14` |
| fail | 失败 | 红，基于 `#ff4d4f` |
| error | 异常 | 灰，基于 `#8c8c8c` |
| skip | 跳过 | 蓝，基于 `#1677ff` |

状态不应只依赖颜色，还需要文字标签。统计块、Tag、Badge、表格状态列都应使用同一套语义色。

## Typography

- 页面主标题：16px / 600
- 卡片标题：14px / 600
- 正文：14px / 400
- 次要说明：12px
- 数字指标：20px 到 24px / 600
- 任务 ID、路径、规则编码：12px 等宽字体
- 避免超过 20px 的页面标题；工程系统应保持紧凑。

## Components

### Page Header

页面头部应包含：

- 面包屑或页面标题
- 状态摘要
- 主操作
- 次要操作收纳区

主操作最多保留 1 个。低频操作应放入 Dropdown 或 `更多` 菜单。

### Card

卡片用于任务、规则分组、报告块和配置区。

- 卡片标题使用 14px 粗体。
- 每张卡片只表达一个主要对象。
- 状态和关键数字应靠近标题或内容左侧。
- 操作应位于右上或底部，不与状态混排。

### Status Stat

状态统计有三种层级：

1. 全局概览：展示总量，弱化颜色。
2. 任务摘要：突出非零状态，特别是 warn / fail / error。
3. 规则表：使用 Tag 表达状态。

不建议 0 值状态与非零状态使用完全相同的视觉权重。  
可以考虑横向状态分布条、状态 chips 或紧凑统计条。

### Metadata Tag

任务元数据建议用轻量键值展示：

- label：secondary text
- value：primary text
- label 与 value 之间保留 4px 间距
- 避免多个彩色 Tag 增加视觉噪音

示例：

```text
省份 江苏 · 运营商 移动 · 产品 路由器 · 版本 v2.1
```

### Actions

操作分为三类：

| 类型 | 示例 | 展示 |
| --- | --- | --- |
| Primary | 上传数据包、查看报告 | 主按钮或明显链接 |
| Secondary | 详情、日志、重跑 | 文本按钮或链接 |
| Danger | 删除、全量重建 | Dropdown 或危险按钮 + 二次确认 |

删除和全量重建不应与普通浏览操作紧挨平铺。

### Empty State

空状态应包含：

- 简短说明
- 下一步动作
- 必要时提供入口说明

任务列表空状态的主 CTA 应为“上传数据包”。

### Loading State

- 页面级加载使用骨架屏。
- 局部刷新使用轻量 loading。
- 避免整页从骨架屏到内容的大幅跳动。

## Patterns

### Task List

任务列表的核心目标是快速判断：

1. 哪个任务异常？
2. 异常集中在哪些状态？
3. 下一步应该查看详情、报告还是日志？

推荐信息顺序：

1. 任务名称和任务状态
2. fail / warn / error 摘要
3. 元数据
4. 时间和耗时
5. 任务 ID
6. 操作

### Task Detail

任务详情的核心目标是：

1. 了解任务整体健康度
2. 定位失败、告警和异常规则
3. 进入规则详情或查看证据

推荐结构：

1. 面包屑
2. 任务标题和主状态
3. 状态统计
4. 重点关注规则
5. 全部规则
6. 技术信息

### Rule Result

规则详情的核心目标是：

1. 明确结论
2. 展示证据
3. 提供建议
4. 必要时支持单规则重跑

推荐结构：

1. 规则标题、状态、严重度
2. 结论摘要
3. 发现列表
4. 指标或专用检查面板
5. 技术信息

## Do

- 使用一致的间距和圆角。
- 保持状态语义全站统一。
- 让 fail / warn / error 比 pass / skip 更容易发现。
- 收纳低频和危险操作。
- 用可读文本替代 JSON 字符串。
- 使用骨架屏减少页面跳动。

## Don't

- 不要为了视觉丰富牺牲信息密度。
- 不要给 0 值状态过高视觉权重。
- 不要使用过多彩色 Tag。
- 不要加入营销页动效。
- 不要把危险操作与普通操作混排。
- 不要在列表页展开过多次要信息。
