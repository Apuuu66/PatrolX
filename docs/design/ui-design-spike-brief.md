# PatrolX UI Design Spike

本文档记录任务列表与任务详情界面的第一轮设计探索目标。长期 UI 设计约束见
[`docs/design/DESIGN.md`](DESIGN.md)。

## 背景

PatrolX 是离线巡检系统。用户上传 `zip` / `tar.gz` 数据包后生成巡检任务，系统输出规则结果、发现、报告和日志。当前前端使用
React + TypeScript + Vite + Ant Design + ECharts。

本轮只做设计探索，不修改生产代码。OpenDesign 工作区放在仓库外，便于生成候选原型并筛选；确认后的设计约束和组件模式才合并回
PatrolX 仓库。

## 设计方向

### 1. 保守优化

- 保持 Ant Design 企业后台风格。
- 重点优化间距、层级、状态展示和操作分组。
- 目标是最低迁移成本。

### 2. 巡检控制台

- 提高信息密度。
- 强化失败、告警、异常的优先级。
- 适合运维人员快速扫读和排查。

### 3. 简化管理台

- 减少视觉噪音。
- 更强调任务健康度、关键结论和下一步动作。
- 适合管理者或日常巡检查看。

## 任务列表目标

### 关键内容

- 顶部概览：
  - 巡检任务总数
  - 注册规则数
  - 规则结果数
  - 发现问题数
- 任务状态统计：
  - pass 通过
  - warn 告警
  - fail 失败
  - error 异常
  - skip 跳过
- 任务卡片：
  - 任务名称
  - 任务 ID
  - 本地 / 在线模式
  - 创建时间、完成时间、耗时
  - 省份、运营商、产品形态、版本、设备 ID 等元数据
  - 规则状态统计
  - 数据准备状态
- 操作：
  - 常用：详情、报告
  - 低频：重跑、增量重建、全量重建
  - 危险：删除任务
- 状态：
  - 排队中
  - 执行中
  - 已完成
  - 失败
  - 空列表
  - 数据准备异常

### 当前痛点

- 每张任务卡片的五色状态块视觉噪音较高，0 值也占据相同权重。
- 任务 ID 过长，但不是第一优先级信息。
- `重跑 / 重建 / 删除` 与 `详情 / 报告` 平铺，容易误点，也需要更清晰分组。
- 元数据标签的 label 和 value 分隔感不足。
- 数据准备正常时的信息仍然偏多，可以弱化。

## 任务详情目标

### 关键内容

- 任务基本信息：
  - 任务名称
  - 状态
  - 数据包
  - 版本
  - 设备 ID
  - 省份、运营商、产品形态
  - 模式
  - 触发方式
  - 创建时间、完成时间
- 状态统计：
  - pass
  - warn
  - fail
  - error
  - skip
- 重点关注规则：
  - fail
  - warn
  - error
- 全部规则：
  - 可按类别分组：日志、KPI、话统、告警、配置、资源、其他
  - 每条规则显示名称、编码、状态、严重度、结果摘要、耗时、操作
- 操作：
  - 查看报告
  - 查看执行日志
  - 重跑全部
  - 增量重建
  - 单条规则重跑

### 当前痛点

- 顶部操作过多：返回列表、查看报告、执行日志、重跑全部、增量重建全部平铺。
- `重点关注 N 条规则` 提示与下方重点关注表格有重复感。
- 客户信息当前以 JSON 字符串展示，不够友好。
- 全部规则默认折叠，查看时需要多次点击。
- 状态统计卡片支持点击筛选，但选中态不够明显。

## 设计约束

- 桌面优先，不做移动端适配。
- 使用 Ant Design 风格，但可以优化视觉层级。
- 状态色必须保持一致：
  - pass：绿
  - warn：黄
  - fail：红
  - error：灰
  - skip：蓝
- 风格克制、专业，不要营销页感。
- 不要过度动效。
- 保留较高信息密度，但要建立清晰优先级。
- 主操作、次要操作、危险操作必须区分。
- 原型不要求接入真实 API，但要使用真实字段名称和真实业务语义。

## 评估维度

| 维度 | 关注点 |
| --- | --- |
| 信息层级 | 任务名、状态、异常数是否优先 |
| 操作清晰度 | 主操作 / 次要操作 / 危险操作是否分开 |
| 状态可读性 | pass / warn / fail / error / skip 是否一眼可辨 |
| 视觉噪音 | 0 值、次要标签、低频操作是否被弱化 |
| 可实现性 | 是否容易映射到 AntD 组件 |
| 一致性 | 列表、详情、规则页是否使用同一套语言 |

## 交付与合并策略

OpenDesign 产出保留在仓库外设计工作区，不直接进入 `web/src`。每个候选方向应说明：

1. 设计思路
2. 主要变化
3. 状态信息的展示方式
4. 操作分组方式
5. 对现有 AntD 实现的映射难度
6. 适合的场景和取舍

候选方案确认后，将长期规范合并到
[`docs/design/DESIGN.md`](DESIGN.md)，再映射为 React + AntD 组件实现。
