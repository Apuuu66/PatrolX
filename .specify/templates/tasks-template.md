# 任务：[功能名称]

**输入**：来自 `/specs/[###-feature-name]/` 的设计文档

**前置条件**：plan.md（必须）、spec.md（用户故事必须）、research.md、data-model.md、contracts/

**测试**：以下示例包含测试任务。测试为可选——仅在功能规格中明确要求时才包含。

**组织方式**：任务按用户故事分组，以支持每个故事的独立实现和测试。

## 格式：`[ID] [P?] [故事] 描述`

- **[P]**：可并行执行（不同文件，无依赖）
- **[故事]**：该任务所属的用户故事（例如 US1、US2、US3）
- 描述中包含精确的文件路径

## 路径约定

- **单一项目**：仓库根目录的 `src/`、`tests/`
- **Web 应用**：`backend/src/`、`frontend/src/`
- **移动应用**：`api/src/`、`ios/src/` 或 `android/src/`
- 下方路径假设为单一项目——根据 plan.md 结构调整

## 依赖与执行顺序

### 阶段依赖

- **设置（阶段 1）**：无依赖——可立即开始
- **基础层（阶段 2）**：依赖设置完成——阻塞所有用户故事
- **用户故事（阶段 3+）**：均依赖基础层完成
  - 用户故事可并行推进（如有人力）
  - 或按优先级顺序执行（P1 → P2 → P3）
- **收尾（最终阶段）**：依赖所有所需用户故事完成

### 用户故事依赖

- **用户故事 1（P1）**：基础层（阶段 2）完成后即可开始——不依赖其他故事
- **用户故事 2（P2）**：基础层（阶段 2）完成后即可开始——可与 US1 集成但应可独立测试
- **用户故事 3（P3）**：基础层（阶段 2）完成后即可开始——可与 US1/US2 集成但应可独立测试

### 每个用户故事内部

- 测试（如包含）必须在实现前编写并确认失败
- 模型先于服务
- 服务先于端点
- 核心实现先于集成
- 每个故事完成后再进入下一个优先级

### 并行机会

- 所有标记 [P] 的设置任务可并行执行
- 基础层中所有标记 [P] 的任务可并行执行（在阶段 2 内）
- 基础层完成后，所有用户故事可并行开始（如团队产能允许）
- 每个用户故事中标记 [P] 的测试可并行执行
- 同一故事内标记 [P] 的模型可并行执行
- 不同用户故事可由不同成员并行处理

## 实现策略

### MVP 优先（仅用户故事 1）

1. 完成阶段 1：设置
2. 完成阶段 2：基础层（关键——阻塞所有故事）
3. 完成阶段 3：用户故事 1
4. **停止并验证**：独立测试用户故事 1
5. 就绪后部署/演示

### 增量交付

1. 完成设置 + 基础层 → 基础就绪
2. 添加用户故事 1 → 独立测试 → 部署/演示（MVP！）
3. 添加用户故事 2 → 独立测试 → 部署/演示
4. 添加用户故事 3 → 独立测试 → 部署/演示
5. 每个故事增加价值且不破坏先前故事

### 并行团队策略

多人协作时：

1. 团队共同完成设置 + 基础层
2. 基础层完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成并集成

## 注意事项

- [P] 任务 = 不同文件，无依赖
- [故事] 标签将任务映射到特定用户故事以便追溯
- 每个用户故事应可独立完成和测试
- 实现前验证测试失败
- 每个任务或逻辑组完成后提交
- 任何时候在检查点停止以独立验证故事
- 避免：模糊任务、同文件冲突、破坏独立性的跨故事依赖
