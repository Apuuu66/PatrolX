# 研究记录：KPI 跨任务历史趋势

## 1. 设备 ID 修改权限

**决策**：本期将“有权限用户”落地为现有 `admin` 角色。

**理由**：
- 当前系统已区分 viewer/admin，配置类写操作普遍要求 admin。
- 设备 ID 修改会影响跨任务匹配，属于低频但高风险元数据操作。
- 不新增角色模型，避免第二期范围膨胀。

**考虑过的替代方案**：
- 任何登录用户可修改：实现简单，但会造成误改和历史曲线突变风险。
- 新增任务编辑者角色：语义更细，但需要权限模型和界面扩展，超出本期范围。

## 2. 设备 ID 存储

**决策**：复用 `TaskRecord.customer["device_id"]`，并在 `system.customer.device_id`、`task.json` 中同步输出；API `TaskSummary` 增加只读派生字段 `device_id`。

**理由**：
- `customer` 已是任务元数据 JSON，重跑/重建链路已经读取并透传。
- 不需要 SQLite migration，也避免 SQLite 和任务输出出现两套权威值。
- 修改时同时更新 SQLite 和任务输出，保持 output 作为结果唯一数据源。

**考虑过的替代方案**：
- `tasks.device_id` 新列：查询直观，但需要迁移且和 `customer` 元数据重叠。
- 只存 SQLite：违反“output 是任务结果唯一数据源”的现有模式。
- 只存 task.json：pending/running 任务没有可靠 task.json。

## 3. 历史数据读取方式

**决策**：为每个任务生成 JSONL 历史点索引 `output/<task_id>/kpi/history/index.jsonl`，查询时按行读取并过滤。

**理由**：
- 600+ 指标场景不能在查询时全量反序列化旧版大 `system.json` 或 KPI 规则 JSON。
- JSONL 可流式读取，单指标查询内存可控。
- 文件位于任务输出目录内，天然满足任务隔离和级联删除。
- 可由 KPI 测量单元巡检在同一解析结果上生成，避免二次解析 CSV。

**考虑过的替代方案**：
- 扫描每个任务的 KPI 规则 JSON：实现直接，但旧大 JSON会造成内存和延迟问题。
- SQLite 历史点表：查询快，但违反轻量 SQLite定位，删除任务还需要清理数据库。
- 每指标一个文件：单指标打开最快，但行对象/周期命名需要哈希映射，文件数量过多。
- 只支持新任务：实现最少，但既有历史任务无法形成对比。

## 4. 历史索引生命周期

**决策**：KPI 巡检完成时原子写入索引；索引缺失不自动回填，历史查询返回明确降级。

**理由**：
- 查询路径必须可预期，不能因为一次请求隐式重建未知体积的数据。
- 旧任务通过用户显式重建生成索引，保持任务输出不可被查询请求静默修改。
- 任务重跑、全量重建、删除时索引随任务输出刷新或删除。

**考虑过的替代方案**：
- 查询时后台补建：用户体验好，但引入并发写、进度和失败恢复复杂度。
- 全局迁移脚本：可一次性处理，但本期引入额外 CLI/运维入口。

## 5. 时间窗口

**决策**：以当前任务所有有效 KPI 点的最新 UTC 测量时间所在自然日为终点，包含该日往前 6 个自然日。

**理由**：
- 与已澄清规格一致，不使用任务创建/完成时间。
- 使用 UTC 自然日保证存储和排序确定性。
- 全任务最新时间可保证不同指标看到同一历史覆盖窗口，而不是每个指标窗口漂移。

**考虑过的替代方案**：
- 每个指标取自身最新时间：更局部，但同一任务内不同指标窗口不一致。
- 当前任务完成日期：数据可能早于完成日期，跨午夜任务会错位。

## 6. 跨任务冲突

**决策**：先限制候选任务完成时间不晚于当前任务；同维度、同周期、同时间点保留完成时间最新的任务值，完成时间相同按 `task_id` 倒序。当前任务作为查询主体不进入历史候选。

**理由**：
- 避免用当前任务之后完成的“未来数据”解释历史异常。
- 已澄清的“最新完成巡检任务优先”在历史候选内仍然成立。
- `task_id` 倒序提供可复现的平局规则。

**考虑过的替代方案**：
- 跨任务均值：会稀释真实异常，且任务重复上传时难以解释。
- 不处理同时间冲突：图表会出现同一时刻重复点。
- 使用所有任务：实现简单，但可能把较新任务作为旧任务的历史基线。

## 7. 基线和显著偏离

**决策**：使用中位数作为基线，用 MAD 派生鲁棒离散度；样本数不足 3 不判定显著。

**公式**：
```text
scale = 1.4826 * MAD
tolerance = max(3 * scale, 0.10 * max(abs(median), median_abs_dev), 1e-9)
significant = abs(current - median) > tolerance
```

**理由**：
- 中位数比均值更能抵抗离线值和短时尖峰。
- MAD 对少量异常日不敏感。
- 阈值可解释，便于巡检人员理解“显著高于/低于”的判断。

**考虑过的替代方案**：
- 固定百分比阈值：简单，但无法适配不同指标的波动幅度。
- 均值 + 标准差：常用，但少量异常会放大阈值。
- 机器学习模型：样本只有最多 7 个，容易过拟合且难以解释。

## 8. 前端加载策略

**决策**：任务首屏不请求历史；趋势弹窗打开后按当前指标、对象、周期请求一次历史趋势。

**理由**：
- 避免复现 600+ 指标首屏卡顿。
- 历史趋势只在用户主动需要时产生成本。
- 单任务趋势先渲染，历史失败时可回退，不阻断基础能力。

**考虑过的替代方案**：
- 任务详情预取全部历史：响应时间和内存不可控。
- 每个测量单元预取摘要：仍可能产生 22 次请求和 570 指标数据。
- 完全前端聚合：需要下载所有历史任务原始结果，性能最差。
