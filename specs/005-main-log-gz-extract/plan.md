# 实现计划：保留主包解压现场并原地解压日志压缩文件

**分支**：`005-main-log-gz-extract` | **日期**：2026-09-13 | **规格**：[spec.md](spec.md)

**输入**：`/specs/005-main-log-gz-extract/spec.md`

## 摘要

将主包解压语义从“临时解压后搬空删除”改为“保留 `.main/` 原始证据现场，并在分类工作现场生成规则可用副本”。同时把子压缩包展开从单层日志特例升级为通用递归流程：每个子压缩包按自身业务特征分类，可在安全预算内继续展开。日志子包释放出的 `.log.gz` 也按原相对目录展开为 `.log`；成功后 `logs/` 只保留最终解压结果，不保留中间压缩文件。原始上传包与 `.main/` 证据现场保持不可被普通规则消费。

## 技术上下文

**语言/版本**：Python 3.11+；当前本地运行环境使用 Python 3.12。

**主要依赖**：FastAPI、Pydantic v2、structlog、PyYAML；无新增运行时依赖。

**存储**：SQLite 仅承载任务元数据；本功能主要读写任务输出目录文件与解压 manifest。

**测试**：pytest、ruff、本地全流程 `make verify`。

**目标平台**：本地 CLI 与单节点在线 API 共用同一执行器。

**项目类型**：离线巡检后端服务，含本地命令行入口。

**性能目标**：不新增交互接口；任务解压阶段保持顺序执行，资源预算优先于速度优化。

**约束条件**：离线执行；一个上传包对应一个任务输出目录；解压必须防护路径穿越、链接、深度、文件数、单文件大小和总大小；主包解压失败阻断后续阶段；单文件失败不得中断任务。

**规模/范围**：覆盖主包、任意分类子包、多级子包、`.log.gz` 的解压与 manifest 记录；不改变巡检规则业务逻辑，不新增在线 API 字段。

## 技术方案

### 1. 现场模型

任务输出目录采用两个明确区域：

```text
output/<task_id>/
├── .main/                 # 主包原始解压证据现场，保留上传包内部相对结构
├── logs/                  # 分类工作现场，只保留最终日志解压结果
├── kpi/                   # 分类工作现场，只保留最终解压结果
├── ...                    # 其他分类工作现场
├── .patrolx-extracted.json
└── ...
```

- `uploads/` 原始上传包永不修改。
- `.main/` 在任务生命周期内不得删除或清空；只有用户显式删除任务时随任务目录级联删除。
- 普通规则只读取分类工作现场；执行器匹配文件时排除 `.main/`。
- 分类工作现场只保留规则可消费的最终文件；`logs/` 不得保留原始日志子包或 `.log.gz`。

### 2. 主包解压

`pkg.extract.main` 的新语义：

1. 根据上传包 checksum 判断是否需要重建现场。
2. 需要重建时解压到临时目录，校验通过后替换 `.main/`，避免半成品现场。
3. 保留 `.main/` 中上传包的原始目录结构和原始子压缩包。
4. 从 `.main/` 生成分类工作副本：
   - 非压缩文件复制到按业务分类映射的目录；
   - 分类路径保留源文件在 `.main/` 内的相对路径；
   - `.log.gz` 不直接作为工作文件保留，直接进入受控 gzip 展开流程。
5. 对发现的子压缩包登记解压状态，交由分类子包规则继续展开。
6. manifest 记录主包 checksum、原始文件数、现场路径和子包清单。

### 3. 通用递归子包展开

新增 `services/extraction.py` 统一处理子压缩包：

- 分类优先依据子压缩包自身文件名和内容特征；无法识别时继承父级分类或进入可解释的未识别类别。
- 每个待展开子包先进入临时工作区，成功后再落入目标分类目录。
- 递归扫描展开结果；发现的子压缩包按自身特征继续分类和展开。
- 跨分类嵌套允许存在：KPI 子包内发现日志子包时，日志内容进入 `logs/`。
- 使用 checksum 去重防止同一压缩包重复展开和递归爆炸。
- 每次展开都受任务级总预算与既有单包预算约束。
- 单个子包失败记录 `failed`，不影响其他子包和后续巡检。

现有 `pkg.extract.<category>` 规则继续作为隐藏编排入口，但内部调用同一通用服务。这样日志子包中发现 KPI 子包、KPI 子包中发现日志子包时，都可以由当前分类规则触发递归处理，后续分类规则只处理尚未完成的队列项。

### 4. `.log.gz` 展开

`.log.gz` 不作为普通归档子包处理：

1. 在归档展开的临时工作区内识别 `.log.gz`。
2. 以流式方式解压为同目录、同基础文件名的 `.log`。
3. 目标已存在时不覆盖，记录冲突状态。
4. gzip 损坏或超限时记录失败状态。
5. 仅将成功解压的 `.log` 和其他非压缩工作文件放入 `logs/`。
6. manifest 记录来源证据、目标路径、状态和错误。

### 5. manifest 与幂等

`.patrolx-extracted.json` 从单层子包清单升级为版本化解压状态模型，记录主包现场、各级子包、`.log.gz` 展开结果、失败与拒绝项。重跑时：

- 上传包 checksum 未变化且 manifest 完整时复用任务现场。
- 上传包 checksum 变化时重建 `.main/` 和分类工作现场。
- 已成功展开的子包和 `.log.gz` 不重复执行。
- 分类工作现场可依据 manifest 安全重建，但 `.main/` 只能整体替换或保留，不得被普通规则破坏。

### 6. 日志路径与规则兼容

分类工作现场中的日志路径继续保留服务、节点等目录层级。日志规则的 `source_patterns` 最终只匹配 `.log`，不再依赖 `.log.gz` 兜底。该调整属于解压/规则输入逻辑变化，涉及日志规则的 `rule_version` 需要在实现阶段递增。

## 复杂度跟踪

| 违规项 | 为什么需要 | 被拒绝的更简单替代方案及原因 |
| --- | --- | --- |
| 通用递归子包展开服务 | 真实包可能存在 KPI、日志等多分类内的多级嵌套，单层特例会造成遗漏或错误分类。 | 仅在日志规则中递归解压：无法覆盖 KPI 等分类，也会让业务规则承担解压基础设施职责。 |
| 分类工作现场与 `.main/` 证据现场分离 | 既要保留客户原始结构，又要保证普通规则只读取规范化输入，避免重复统计。 | 继续移动并删除 `.main/`：满足规则输入但失去追溯现场。 |
