# 功能规格：单包巡检阶段内并行执行

**功能分支**：`029-stage-parallel-execution`

**创建日期**：2026-10-08

**状态**：已实现

**输入**：用户描述：单个大包跑得慢；不考虑解压耗时和单条规则耗时；用并发优化单任务执行时长；先固定 4 个执行进程；采用保守方案（保留 EXTRACT → PREPARE → INSPECT 阶段屏障）；后续版本再放开 prepare 只能被 owner 规则使用的限制。

## 背景

单包巡检任务的执行链为 `EXTRACT → PREPARE → INSPECT → 收尾`，目前阶段内逐单元串行执行。包越大（规则越多、日志越大），用户等待越久。静态依赖审计确认：PREPARE 单元之间无数据依赖，普通规则之间无数据依赖；真实顺序依赖只有三条——主包解压先于其余全部、owner 的 prepare 先于 owner 规则、全部执行结果先于收尾落盘。

实测基准（16 个日志文件、88.8MB、约 64 万条记录、10 条日志规则）：

- 串行规则阶段约 14.9 秒；其中 `log.fault_pattern` 单条 4.45 秒、`log.repeat_error` 单条 2.80 秒。
- 4 并行执行约 5.4 秒（约 2.75 倍加速）。
- 并行度提高到 10 后墙钟不再下降（最慢单条规则构成下限），峰值内存却从 1.9GB 增至 4.2GB。

本功能为任务内执行引入固定 4 并行度：PREPARE 阶段内并行执行、INSPECT 阶段内并行执行；两个阶段之间保留全局屏障（保守方案），即全部 PREPARE 完成后才开始 INSPECT。保守方案保证执行顺序、结果语义与失败隔离与现行契约完全一致，并行等价性可按“串行/并行结果逐字段一致”验收。

后续方向（不在本版范围）：放开“prepare 只能被 owner 规则消费”的限制，让公共准备数据可被多条规则共享消费；该变更涉及项目宪法修订，需独立走 Speckit 流程。本版不改动 prepare 私有契约，也不引入共享 prepared 数据。

范围外：解压耗时优化、单条规则内部优化（含按文件或字节切分的 chunk 级并行）、KPI 专项优化、跨任务并发、prepare 共享消费。

## Clarifications

### Session 2026-10-08

- Q: 并行执行采用什么阶段模型？ → A: 保守方案：保留 `EXTRACT → PREPARE → INSPECT → 收尾` 全局阶段屏障，只在阶段内并行；解压与收尾保持串行。
- Q: 并行执行单元应该用线程还是进程？ → A: 用进程。规则以解析大文件为主、属 CPU 密集，线程受 GIL 限制（实测约 1.00x，无加速）。
- Q: 并行度如何确定，是否提供配置项？ → A: 固定 4 个执行进程；阶段内待执行单元少于 4 时按实际数量执行；本版不提供任何并行度配置项。
- Q: 是否在本版放开“prepare 只能被 owner 规则消费”的限制？ → A: 不放开。本版保持 prepare 私有语义不变；多规则共享 prepared 数据作为后续独立版本，需先修订宪法与相关契约。
- Q: 解压耗时、单条规则内部耗时、KPI 专项与跨任务并发是否纳入本版？ → A: 都不纳入；本版只做任务内阶段内并行，其余列入范围外。

## 用户场景与测试

### 用户故事 1 - 大包任务显著提速且结果不变（优先级：P1）

用户上传大包并执行巡检，规则阶段的墙钟从串行基线显著下降；任务详情、报告与规则 JSON 与串行执行结果一致。

**优先级理由**：单包执行时长直接决定用户等待体验，是本功能的核心目标。

**独立测试**：对同一基准包分别以串行基线与 4 并行度执行，测量墙钟并比对全部执行单元结果、任务摘要与报告。

**验收场景**：

1. **给定** 包含多条规则与大量日志的基准包，**当** 执行任务，**则** 任一 INSPECT 规则开始前，全部 PREPARE 单元均已完成（阶段屏障在时间线上可验证）。
2. **给定** 同一基准包分别串行与并行执行，**当** 比对结果，**则** 全部执行单元的状态、发现、指标、skip 原因与摘要逐字段一致（执行时间等时间字段除外），任务摘要与报告一致。
3. **给定** 4 物理核以上的基准机，**当** 执行基准包任务，**则** 规则阶段墙钟不高于串行基线的 50%。
4. **给定** 仅含少量执行单元（如 1~2 个）的小任务，**当** 执行，**则** 总时长相对串行基线劣化不超过 10%。

### 用户故事 2 - 单执行单元失败被隔离（优先级：P1）

任一 prepare 或规则失败、异常或 worker 非正常退出时，仅该单元受影响；任务继续，失败原因可解释。

**优先级理由**：并行引入进程边界后，必须保证现行“单文件解析失败不中断任务”的隔离语义不回退。

**独立测试**：分别注入 prepare 失败、规则异常、worker 非正常退出三种故障，观察其余单元结果与任务状态。

**验收场景**：

1. **给定** 某 prepare 执行失败，**当** 任务执行，**则** 仅其 owner 规则以 skip/error 结束并携带明确原因；其余单元结果与无故障基线一致。
2. **给定** 某条规则抛出异常或对应 worker 非正常退出，**当** 任务执行，**则** 仅该规则记为 error 并包含错误摘要，其余单元继续完成。
3. **给定** 任一上述故障场景，**当** 任务结束后检查，**则** 无残留子进程，且任务可通过既有重建/重跑能力恢复。

### 用户故事 3 - 日常操作与单规则重跑语义不变（优先级：P2）

CLI、API、`verify-one` 单规则重跑、任务详情与报告展示的行为与并行前一致。

**优先级理由**：并行是执行层优化，不应改变任何既有对外行为。

**独立测试**：运行单规则重跑并检查文件改动范围；对比 CLI 与 API 双模式执行结果。

**验收场景**：

1. **给定** `python build.py verify-one --rule <rule_code>`，**当** 执行，**则** 只执行或复用目标规则私有 prepare 与目标规则，其他规则 JSON 不变。
2. **给定** 同一任务分别通过 CLI 与 API 执行，**当** 比对结果，**则** 两者一致。
3. **给定** 并行执行完成的任务，**当** 打开任务详情与报告，**则** 字段、规则顺序与内容与串行执行一致。

### 边界情况

- 阶段内执行单元数少于 4（含只有 1 个 prepare 的情况）时按实际数量执行，不空转等待。
- 无匹配文件、格式不适用或解析失败时仍返回 skip + skip_reason；全部规则 skip 时任务仍成功完成。
- 多进程并发记录执行日志时，日志行必须完整不交错，顺序稳定可预期。
- 规则 JSON、任务摘要与报告必须由单一写入者按既有计划顺序落盘。
- prepare 缓存命中（HIT）与免重建语义不受并行影响。
- 单 worker 峰值内存随任务规模放大；4 并行度下的峰值内存必须可度量，不得导致宿主内存耗尽且不可解释。
- 任务运行期间的删除操作仍按现状被拒绝（BUSY）；并行不得改变该协调语义。
- 已存在任务现场的重建/重跑（全量、增量、单规则）必须与并行执行兼容。

## 需求

### 功能需求

- **FR-001**：系统必须在同一任务内并行执行 PREPARE 阶段单元，最大并行度为 4。
- **FR-002**：系统必须在同一任务内并行执行 INSPECT 阶段规则，最大并行度为 4。
- **FR-003**：系统必须保留 EXTRACT → PREPARE → INSPECT → 收尾的全局阶段屏障：全部 PREPARE 完成后才允许任何 INSPECT 规则开始；解压与收尾保持串行。
- **FR-004**：并行执行结果必须与串行执行结果逐字段一致（执行时间等时间字段除外），包括每个单元的状态、发现、指标、skip 原因、任务摘要与报告。
- **FR-005**：单个 prepare 失败必须只影响其 owner 规则（skip/error + 明确原因），不得中断其他单元。
- **FR-006**：单条规则异常或 worker 非正常退出必须被隔离为该规则 error；其余单元继续执行。
- **FR-007**：并行化不得引入规则间数据访问；每条规则仍只能读取自己 source_patterns 匹配的文件与私有 prepared 数据（现行宪法约束不变）。
- **FR-008**：结果落盘必须由单一写入者按既有计划顺序执行（规则 JSON、任务摘要、报告），不得出现交错或乱序。
- **FR-009**：执行日志必须保证行完整性与稳定顺序。
- **FR-010**：单条规则的 duration_ms 只统计其自身执行耗时，不包含排队等待。
- **FR-011**：并行度固定为 4；阶段内单元数少于 4 时按实际数量执行。本版不提供并行度配置项。
- **FR-012**：并行执行引入的固定开销必须受控：执行单元很少或数据量很小的任务，总时长相对串行基线劣化不超过 10%。
- **FR-013**：任务结束后必须回收全部并行执行资源，不得残留子进程。
- **FR-014**：prepare 缓存标记、命中/重建语义与单规则重跑行为必须保持不变。
- **FR-015**：并行执行的峰值资源开销必须可度量（至少内存），并在任务执行日志中可观测。
- **FR-016**：仓库内必须提供可复现的基准资产（基准包生成脚本或样例数据）与串行/并行等价性自动化测试，作为验收依据。
- **FR-017**：本功能不得改变既有规则元数据、结果契约字段含义与任务目录布局；如执行契约文档需同步更新，必须一并更新。
- **FR-018**：本功能不得改变任何规则的判定逻辑；规则版本不因执行器并行化而变化（如行为有变化，必须按宪法升级 rule_version）。

### 关键实体

- **执行单元**：可独立调度的最小执行单位，包括隐藏的 PREPARE 单元与普通规则；本功能的并行调度粒度。
- **阶段屏障**：EXTRACT、PREPARE、INSPECT 阶段之间的就绪栅栏，保证 prepare 完成先于依赖它的规则。
- **规则结果（RuleResult）**：既有契约实体，字段含义不变。
- **基准用例**：可复现的样例包与测量/比对脚本，用于等价性与提速验收。

## 成功标准

### 可度量结果

- **SC-001**：在 4 物理核以上基准机上执行基准包（约 88MB 日志、≥10 条规则），规则阶段墙钟相对串行基线下降 ≥50%（实测参考 2.7 倍以上）。
- **SC-002**：串行与并行的全部执行单元结果逐字段一致率为 100%（执行时间等时间字段除外），任务摘要与报告一致。
- **SC-003**：三类故障注入（prepare 失败、规则异常、worker 非正常退出）下任务仍完成，失败单元原因可解释，其余单元结果与无故障基线的逐字段一致率为 100%。
- **SC-004**：4 并行度峰值内存不超过串行单进程峰值的 4 倍（允许 10% 误差），且基准机不触发交换。
- **SC-005**：单规则重跑仅改动目标规则 JSON、任务摘要与报告，其他规则文件改动数为 0。
- **SC-006**：任务执行结束后子进程残留数为 0。
- **SC-007**：小任务（1~2 个执行单元）总时长相对串行基线劣化 ≤10%。

## 假设

- 目标部署机至少 4 个逻辑核；固定并行度 4 为本版产品决策，暂不开放配置。
- 同一时刻只执行一个巡检任务（任务队列串行消费）；本功能只做任务内并行，不做跨任务并行。
- 实际并行度取“阶段内待执行单元数”与 4 的较小值。
- 结果契约、任务目录布局、prepare 缓存语义与重跑语义保持不变。
- 放开 prepare 共享消费为后续独立版本，需先修订宪法与相关契约，不在本版实现；本版暂不引入共享 prepared 数据。
- chunk 级切分、KPI 专项与解压耗时优化不在本版；若后续基准显示单条规则长尾仍主导墙钟，再按需立项。
- 进程创建方式与预热/复用策略由设计阶段决定；本版只要求固定开销受控（FR-012）。
- 仓库当前没有可复现的性能基准资产，需要在本功能内补齐（FR-016）。
