# 功能规格：未清除告警与反复上报巡检

**功能分支**：`feature/039-alarm-active-recurrence`

**创建日期**：2026-11-04

**状态**：已澄清

**输入**：用户描述：“看下当前告警文件，有哪些巡检建议，优先做哪些；关注未清除、非操作时间闪断、告警反复上报和总次数；单独分析告警文件即可，不需要跨文件。”

## 背景

当前任务的告警文件只包含两张告警 CSV，共 2,209 条有效记录、44 种告警。只读盘点发现：

- 未清除 16 条，其中 Critical 1 条、Major 11 条、Minor 4 条；
- `Repeat Times > 0` 的历史记录 584 条，原始 `Repeat Times` 合计 43,762；
- 若按“首报 + `Repeat Times` 次重复”估算，全部告警约 45,971 次上报；
- 16 条未清除告警自身累计原始 `Repeat Times` 41,776，估算约 41,792 次上报；
- 单条最大 `Repeat Times` 为 41,695，是一条持续约 22.75 天且仍未清除的 NTP 同步失败告警；
- `137611` iBMC 连接失败有 1,581 条生命周期记录、原始 `Repeat Times` 合计 1,218、单条最大 193；
- 另有 28 条 License 未加载记录全部 `Repeat Times=0`，说明只看重复次数会漏掉“多次独立发生但每次未重复上报”的告警。

因此，优先需要回答两个问题：

1. **现在还有什么没有清除，风险是否在持续放大。** 只看“历史告警总量”会把 16 条活动告警淹没在 2,209 条历史记录中；只看当前状态又会漏掉持续重复上报形成的风险。
2. **同类告警是否在反复发生、累计上报了多少。** 只看生命周期条数会漏掉单条记录内部的 `Repeat Times`，只看 `Repeat Times` 又会漏掉“每次都不重复、但发生很多次”的告警。

本功能新增两条独立 P1 告警规则，在不读取操作日志、License、NTP、证书状态或其他文件的前提下，仅分析 `alarm/*.csv`：

- `alarm.active_state`：列出未清除告警，并按严重级、持续时长和原始/估算上报次数排序。
- `alarm.recurrence`：按告警类型汇总全部生命周期，提供对象明细、反复发生、短告警、快速复发、状态分布和累计上报次数。

两条规则独立解析输入，不互相调用、不消费对方结果。历史 `alarm.flapping` 规则及其 `metadata.alarm_flapping` 契约不恢复、不重定义；新旧结果使用不同规则代码和元数据命名空间。

**范围边界**：

- 只分析规范化任务目录下直接位于 `alarm/` 且扩展名为 `.csv` 的文件。
- 不分析其他目录、其他扩展名、嵌套目录中的 CSV、操作日志、License、NTP 状态、证书配置或跨任务数据。
- 不判断“计划内/计划外”或“操作时间/非操作时间”；仅告警文件无法可靠证明现场是否进行了操作。原始时间、持续时长和快速复发证据用于人工判断，系统不得把某个时间窗直接称为操作窗。
- 不因缺少跨文件证据而宣称告警已稳定恢复；`Reset Cleared` 只能视为“清除状态被重置”，不能视为稳定恢复。

告警导出存在中文和英文两种口径。当前现场文件使用英文表头和英文状态，历史样例或其他产品版本可能使用中文表头、中文状态和中文严重级。本功能按“字段别名 + 状态/严重级/对象键归一化”设计，并预留集中式术语映射：后续补充权威中英文映射时只扩展映射与测试，不改变两条规则的判定语义。未知术语必须保留为可审计的未知值，不得静默错映射。

## Clarifications

### Session 2026-11-04

- Q: 本功能是否读取告警以外的文件或做跨任务分析？ → A: 不读取。只分析规范化任务目录下直接位于 `alarm/` 的 `.csv`；同一任务内可读取多个告警 CSV，但不得读取操作日志、配置、状态文件或跨任务数据。
- Q: 是否恢复历史 `alarm.flapping`？ → A: 不恢复。新增 `alarm.active_state` 与 `alarm.recurrence`，旧规则和 `metadata.alarm_flapping` 契约保持历史只读含义。
- Q: 如何同时处理中英文告警导出？ → A: 使用集中式可扩展映射统一表头、状态、严重级和对象键；当前已知中英文口径先纳入，权威映射可由用户后续补充，未知术语按未知值审计。
- Q: `Repeat Times` 如何转成“总次数”？ → A: 原始 `Repeat Times` 合计与 `Σ(1 + Repeat Times)` 估算上报总数分别展示；后者明确标注为估算，不宣称精确事件总数。
- Q: 是否能判断非操作时间或计划外闪断？ → A: 不能仅凭告警文件可靠判断现场操作。规则只输出时间、持续时长、生命周期次数、重复次数和快速复发事实，不把任何时间窗称为操作窗或非操作时间。
- Q: 无时区时间如何解释？ → A: 按告警数据所属现场统一的 UTC+8 解释，再转 UTC 存储；带偏移时间统一转 UTC。
- Q: 闪断/反复的默认判定口径？ → A: 单次已清除持续不超过 300 秒记为短告警；60 分钟内至少出现 3 次记为快速复发。两者均作为可回显参数，事实汇总不受参数关闭影响。
- Q: `Reset Cleared` 如何处理？ → A: 不计为活动告警；计入状态分布和“清除状态被重置”标记，但不得被判为稳定恢复。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 先看到仍未清除的告警和风险排序（优先级：P1）

值班人员打开任务规则详情或报告时，首先看到当前仍未清除的告警。每条告警显示严重级、告警名称、应用、对象、首次上报时间、截至告警数据末刻的持续时长、原始 `Repeat Times` 和估算上报次数；列表优先展示 Critical、持续重复上报、持续时间长的告警。

**优先级理由**：未清除告警是当前仍可能造成业务影响的活动风险，也是用户明确要求优先查看的内容。没有这一视图，持续 20 多天、重复数万次的告警会被历史总量掩盖。

**独立测试**：使用包含 Critical、Major、Minor 未清除记录及已清除记录的合成告警文件执行 `alarm.active_state`，验证活动告警数、严重级分布、原始重复次数合计、最大单条重复次数、估算上报次数和排序。再删除 `Whether Cleared=Not Cleared` 记录，验证规则不再产生活动告警 Finding。

**验收场景**：

1. **给定** 告警 CSV 含 3 条 `Not Cleared`、2 条 `Normal Cleared`、1 条 `Reset Cleared`，**当** 执行规则，**则** 只把 3 条 `Not Cleared` 计为活动告警，`Reset Cleared` 不计为活动告警但保留在状态统计中。
2. **给定** 活动告警分别为 Critical、Major、Minor，**当** 生成 Finding 和明细，**则** 按 Critical、Major、Minor 排序，同级按原始 `Repeat Times` 合计降序，再按持续时长降序。
3. **给定** 三条活动告警的 `Repeat Times` 分别为 0、2、5，**当** 生成指标，**则** 原始重复次数合计为 7，估算上报次数为 `(1+0)+(1+2)+(1+5)=10`，单条最大为 5。
4. **给定** 存在当前活动告警，**当** 规则生成，**则** 持续时长统一计算到告警文件覆盖末刻，并明确该时刻不是任务上传或执行时刻。
5. **给定** 文件中有已清除记录但没有未清除记录，**当** 执行规则，**则** 规则为 `pass`，活动告警计数为 0，并保留状态分布供审计。

---

### 用户故事 2 - 识别反复发生并核对累计上报次数（优先级：P1）

值班人员需要判断同一告警是否反复发生，以及累计上报次数是否异常。规则按应用和告警 ID 汇总全部状态的生命周期，提供对象分布、生命周期次数、原始 `Repeat Times` 合计、最大单条重复次数、估算上报次数、首次/最近出现时间、最长持续时长和最短复发间隔；同时标识短告警、60 分钟内反复出现、持续期内重复上报及 `Reset Cleared`。

**优先级理由**：用户明确要求“告警反复上报、总次数也看看”。重复次数与生命周期次数是两种不同证据，任一单独使用都会低估或误判反复问题。

**独立测试**：使用覆盖正常清除、未清除、`Reset Cleared`、短告警、60 分钟内反复发生、单条高 `Repeat Times` 和多次零重复发生的合成文件执行 `alarm.recurrence`，验证类型汇总与对象明细同时正确，且不依赖 `alarm.active_state` 的产物。

**验收场景**：

1. **给定** 同一应用、同一告警 ID 有 3 条生命周期记录，`Repeat Times` 分别为 0、1、4，**当** 执行规则，**则** 生命周期次数为 3，原始重复次数合计为 5，估算上报次数为 8，最大单条为 4。
2. **给定** 同一告警在 60 分钟内出现 3 次，其中至少一次持续时间不超过 5 分钟，**当** 执行规则，**则** 同时标识“快速复发”和“短告警”，但不声称其发生在操作时间之外。
3. **给定** 同一条告警只有 1 条生命周期记录但 `Repeat Times=100`，**当** 执行规则，**则** 标识“持续期内重复上报”，不能因为生命周期次数为 1 而忽略累计重复次数。
4. **给定** 同一告警有 20 条生命周期记录且每条 `Repeat Times=0`，**当** 执行规则，**则** 仍标识为多次发生，不能因为原始重复次数为 0 而判为无反复。
5. **给定** 告警状态为 `Reset Cleared`，**当** 生成恢复相关分组，**则** 计入状态分布和“清除状态被重置”标记，但不得进入“稳定恢复”或等价结论。
6. **给定** 同一告警发生在多个对象上，**当** 汇总告警类型，**则** 类型总次数包含全部对象，同时对象明细分别可读，不得因对象拆分而丢失类型总次数。

### 边界情况

- 没有任何 `alarm/*.csv` 时，两条规则均返回 `skip` 并写明无匹配告警 CSV。
- 有 CSV 但缺少必要表头、零数据行或全部记录无法解析时，返回 `skip` 并写明格式不适用或无可解析记录。
- 单文件损坏、编码失败或 CSV 解析失败时只影响该文件，其他文件继续分析；失败文件数必须可见，不得静默通过。
- `Whether Cleared` 为空或未知时，不得擅自当作 `Not Cleared`；该记录计入排除行与原因统计。
- `Raised Time` 不可解析时，记录不得参与时间排序、持续时长和间隔计算，并计入排除行；若因此没有可分析记录，返回 `skip`。
- `Cleared Time` 早于 `Raised Time` 时，记录保留在状态与重复次数统计中，但持续时长与间隔判据标记不可用，并计入异常时长记录。
- `Repeat Times` 缺失、空值、负数或非整数时，不猜测其数值；记录可保留在状态与生命周期统计中，但原始重复合计和估算上报次数必须标记为不完整，并输出无效值记录数。
- `App Name`、`Alarm ID` 或 `Alarm Name` 缺失时，使用稳定占位并在结果中显式标记，不得让记录静默消失。
- 对象无法从 `Pod Name`、`Located Device`、`Service Name`、`Alarm Source` 等稳定字段解析时，使用稳定占位并保留来源文件与行号，不能把整段可变描述当作对象键。
- 多个告警文件存在完全相同记录时只计一次，并输出重复行数；生命周期或重复次数不同的记录不得被合并。
- 同一告警的 `Repeat Times` 为 0 但存在多条独立生命周期时，仍必须进入反复发生候选。
- 告警数据覆盖期很短或不连续时，输出实际覆盖起止和记录数，不基于观察窗推断“稳定恢复”。
- 输入时间无时区时按包内告警数据统一的 UTC+8 现场时间解释并转为 UTC；带偏移输入统一转为 UTC。这项假设必须出现在结果元数据中。
- 超大文件或记录数超过安全预算时，规则应明确降级或跳过并给出原因，不得耗尽任务进程资源。

## 需求 *(必填)*

### 功能需求

#### 输入、隔离与契约

- **FR-001**：系统必须新增独立普通规则 `alarm.active_state`，分类为告警类、优先级 P1，并声明完整规则元数据、输出指标和初始 `rule_version`。
- **FR-002**：系统必须新增独立普通规则 `alarm.recurrence`，分类为告警类、优先级 P1，并声明完整规则元数据、输出指标和初始 `rule_version`。
- **FR-003**：两条规则都必须只通过各自的 `source_patterns` 或稳定扫描组匹配规范化任务目录下直接位于 `alarm/` 的 `.csv` 文件，不得读取其他业务目录或其他扩展名文件。
- **FR-004**：两条规则必须独立解析告警文件；不得互相导入、实例化、调用、读取对方 JSON，或消费对方 prepared 数据。
- **FR-005**：系统不得恢复历史 `alarm.stat` 或 `alarm.flapping` 规则，不得重定义或复用 `metadata.alarm_flapping` 的既有字段含义。新结果必须分别使用独立的 `metadata.alarm_active` 与 `metadata.alarm_recurrence` 命名空间。
- **FR-006**：本功能只新增规则结果元数据、指标和 Finding，不新增 HTTP 接口，也不修改既有 `RuleResult`、`Metric`、`Finding` 字段语义；如实现必须新增公共契约字段，应先更新 OpenAPI 再实现。

#### 共用解析口径

- **FR-007**：解析必须兼容 UTF-8（含 BOM）、字段名大小写和首尾空白，并同时支持中英文表头别名；至少识别 `Whether Cleared`、`Repeat Times`、`Raised Time`、`Cleared Time`、`Alarm Severity`、`App Name`、`Alarm ID`、`Alarm Name`、`Serial No.`、`Location Info` 和 `Additional Information` 及其已登记中文别名。
- **FR-008**：字段值必须去除首尾空白；中英文状态值必须归一化为 `Not Cleared`、`Normal Cleared`、`Reset Cleared` 和 `Unknown`，不得仅凭 `Cleared Time` 是否为空改变状态语义。中英文严重级必须归一化为既有 `CRITICAL/HIGH/MEDIUM/LOW` 语义；未知状态或严重级不得静默猜测。
- **FR-009**：带偏移的时间必须转换为 UTC；无偏移时间必须按包内告警数据统一的 UTC+8 现场时间解释后转换为 UTC。所有输出时间字段使用 `*_at` 命名并序列化为带时区的 ISO-8601。
- **FR-010**：告警数据覆盖末刻必须取全部有效 `Raised Time` 与 `Cleared Time` 的最大值。未清除告警的持续时长计算到该末刻，并在元数据中注明这是“告警数据末刻”，不是任务执行时刻。
- **FR-011**：跨文件完全相同的记录必须去重并计数；单个文件解析失败不得中断其他文件，规则必须输出失败文件数及相对路径列表。
- **FR-012**：无匹配文件、格式不适用或没有可分析记录时，两条规则必须返回 `skip` 和明确的 `skip_reason`；单文件或单记录失败不得导致整个任务失败。
- **FR-036**：系统必须以集中式、可扩展映射维护告警表头别名、状态同义词、严重级同义词和对象键别名；映射必须同时覆盖英文和已登记中文口径，禁止把中英文判断散落在规则逻辑中。
- **FR-037**：映射不命中时，原始表头、状态或严重级必须以未知值及其出现次数进入元数据或质量统计，不得丢弃整行、猜测为活动告警或猜测为稳定状态。后续补充权威映射时不得改变既有规范化值的含义。
- **FR-038**：测试必须覆盖纯英文文件、纯中文文件、同一任务混合中英文文件三种情况，并断言同一告警在两种语言口径下产生相同的规范化状态、严重级、对象和累计结果。

#### 活动告警规则

- **FR-013**：`alarm.active_state` 必须以 `Whether Cleared=Not Cleared` 作为唯一活动状态判据，`Normal Cleared` 与 `Reset Cleared` 均不得计入活动告警。
- **FR-014**：活动告警明细必须至少包含告警 ID、告警名称、应用、归一化对象、严重级、首次上报时间、持续秒数、原始 `Repeat Times`、估算上报次数、来源文件和行号。
- **FR-015**：规则必须输出当前活动告警记录数、活动告警分组数、严重级分布、`Not Cleared`/`Normal Cleared`/`Reset Cleared` 状态分布、活动记录原始重复次数合计、单条最大原始重复次数和活动记录估算上报总数。
- **FR-016**：估算上报总数必须定义为所有有效记录的 `Σ(1 + Repeat Times)`，并明确标注为“估算”；原始 `Repeat Times` 合计必须单独输出，不能用一个字段混淆两种口径。
- **FR-017**：活动告警 Finding 和明细必须按严重级、原始重复次数、持续时长依次降序排列；Critical 或 Major 活动告警存在时规则状态不得为 `pass`。
- **FR-018**：没有活动告警但存在有效告警记录时规则为 `pass`；只有 Minor、Warning 或未知严重级活动告警时至少为 `warn`；存在 Critical 或 Major 活动告警时规则为 `fail`。
- **FR-019**：活动告警的告警类型汇总必须提供原始重复次数与估算上报次数，使持续重复上报的大单条告警能够排在仅持续很久、但重复次数为 0 的告警之前。

#### 反复上报规则

- **FR-020**：`alarm.recurrence` 必须分析全部状态的有效生命周期记录，不得只分析 `Not Cleared` 记录。
- **FR-021**：告警类型汇总键必须至少为 `App Name + Alarm ID`，并保留告警名称、严重级分布和状态分布；对象必须作为独立明细维度，不能因按对象拆分而丢失类型总次数。
- **FR-022**：对象归一化必须优先使用结构化稳定字段，至少支持 `Pod Name`、`Located Device`、`Service Name` 和 `Alarm Source` 及其已登记中英文别名；解析失败时使用稳定占位并保留来源引用，禁止使用整段可变描述直接分组。
- **FR-023**：每个告警类型和对象明细必须输出生命周期次数、原始 `Repeat Times` 合计、最大单条原始重复次数、估算上报次数、首次与最近上报时间、最长持续秒数、最短相邻上报间隔和状态分布。
- **FR-024**：规则必须分别标识至少以下事实或标记：`multi_lifecycle`（生命周期次数大于 1）、`repeat_reporting`（原始重复次数合计大于 0）、`short_alarm`（存在不超过 300 秒的已清除生命周期）、`rapid_recurrence`（60 分钟内出现至少 3 次）和 `reset_cleared`（存在 `Reset Cleared`）。
- **FR-025**：`short_alarm_sec`、`rapid_recurrence_window_sec` 和 `rapid_recurrence_min_count` 必须作为有默认值的规则参数公开，默认分别为 300 秒、3,600 秒和 3 次；规则结果必须回显本次生效参数。
- **FR-026**：`Repeat Times > 0` 的单条生命周期必须能够独立触发“持续期内重复上报”证据，即使该告警只有一个生命周期；生命周期次数大于 1 且所有 `Repeat Times=0` 时仍必须触发“多次发生”证据。
- **FR-027**：`Reset Cleared` 必须计入状态分布和清除状态被重置标记，但不得被描述为稳定恢复、根因已消除或已验证恢复。
- **FR-028**：反复上报 Finding 必须优先展示“未清除且有重复上报/快速复发”的类型，其次展示短告警或已清除但反复上报的类型；无反复证据时规则为 `pass`，只有已清除反复证据时至少为 `warn`。
- **FR-029**：规则不得根据某条告警之后没有更多记录推断稳定恢复；只能陈述告警数据覆盖末刻前的已观察事实。

#### 展示、解释与可追溯性

- **FR-030**：规则详情页必须分别展示活动告警和反复上报的结构化明细，使值班人员无需读取原始 CSV 即可看到严重级、对象、持续时长、生命周期次数、原始重复次数、估算上报次数和证据标记。
- **FR-031**：HTML 报告必须包含活动告警数、未清除最高严重级、原始重复次数合计、估算上报总数和优先处置建议；详细分组可保留在规则结果元数据中。
- **FR-032**：所有 Finding 的 `finding_id` 必须在同一任务和规则内稳定、唯一、可幂等重跑，并能通过来源文件与行号回溯到证据。
- **FR-033**：结果必须提供覆盖起止、有效记录、排除记录、重复记录、失败文件及上限截断状态；任何截断都不得改变汇总总数。
- **FR-034**：本地 CLI、在线 API 和单规则重跑必须对同一输入产生相同规则状态、指标、Finding 语义和元数据（执行标识与时间除外）。
- **FR-035**：现有 `kpi.measurement_units` 规则及其结果契约不得因本功能改变；新增告警规则只能通过规则注册和扫描组启用。

### 关键实体

- **告警记录**：一条告警生命周期，包含应用、告警 ID/名称、严重级、状态、上报时间、清除时间、对象、原始重复次数和来源位置。
- **活动告警分组**：仍未清除的告警按应用、告警 ID 和归一化对象聚合后的当前风险，含持续时长和重复上报量。
- **告警类型汇总**：同一应用和告警 ID 在全部对象上的生命周期与累计重复次数，用于判断整体反复程度。
- **对象明细**：告警类型在具体 Pod、设备、服务或告警源上的生命周期与上报次数，用于定位处置对象。
- **覆盖信息**：由有效告警时间推导的数据起止、记录数和数据质量计数，用于说明所有时长、排序和缺失判断的边界。

## 假设

- `Repeat Times` 按“首次上报之外的重复次数”解释，因此 `1 + Repeat Times` 仅是估算上报次数，不是数据源已确认的精确事件总数；如果后续获得字段权威定义，应通过新规则版本修正展示口径，不回写既有结果含义。
- 无时区告警时间来自同一现场时区，按 UTC+8 解释；这是与既有巡检和项目时间处理一致的工程假设，不改写源文件。
- 告警 CSV 已由分类阶段安全放入任务内 `alarm/`，本功能不负责解压、分类或修复来源包。
- 当前数据只包含告警文件，操作日志、维护计划和状态配置不在本功能可用证据范围内。
- 告警数据末刻只表示可获得证据的最后时刻，不等同于采集完成时间、任务完成时间或告警真实恢复时间。
- 现有规则注册表、扫描组配置、通用 `RuleResult` 展示和报告框架可复用，不需要新增 HTTP API。
- 当前已知映射来自现有告警导出和项目合成样例；权威中英文术语表可在实现前或实现后由用户补充。映射扩展不得改变规则版本以外的判定语义，未知术语在补充前按未知值审计。
- 如果数据量超过规则安全预算，允许在明确记录截断原因后只展示 Top-N 明细，但全部汇总指标必须基于完整有效数据。
