## Clarifications

### Session 2026-09-14

- Q: 项目应如何处理现有的 Makefile 和本地启动 shell 包装脚本？ → A: 删除 Makefile 和相关本地启动 shell 包装脚本，仅保留统一 Python 入口；部署环境所需的构建脚本后续单独开发。
- Q: 统一 Python 入口在干净环境中是否必须只依赖官方 Python 自带能力就能启动并完成依赖安装？ → A: 仅要求官方 Python；统一入口自身和后端依赖安装只使用 Python 自带能力完成。
- Q: 统一入口在干净环境中应采用哪种调用形式？ → A: 使用 `python build.py <操作> [参数]`。
- Q: 迁移后应如何处理当前仓库中的 uv 专用约定？ → A: 彻底去掉 uv；删除 `uv.lock`，并移除活跃配置、文档和入口中的 uv 专用约定，历史归档不改写。
- Q: 依赖版本如何管理？ → A: 依赖版本必须精确锁定；`requirements-lock.txt` 是唯一权威锁，标准安装不得重新放宽解析依赖版本。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 新成员零 Make 完成基础流程（优先级：P1）

一名新成员在拿到代码库后，希望按照项目文档完成依赖安装和本地巡检全流程。无论其使用 macOS、Linux 还是 Windows，只要具备项目声明的基础运行环境，就能使用同一条构建入口完成任务，而不需要先确认系统是否提供 GNU Make 或理解 Make 语法。

**优先级理由**：这是降低平台依赖的核心价值；如果基础流程仍强制依赖 Make，本功能无法成立。

**独立测试**：在一台未安装 GNU Make 的环境中，按权威文档从干净检出开始执行依赖安装和本地全流程，并确认生成正常的巡检任务产物。

**验收场景**：

1. **给定** 一份干净的项目检出和符合要求的运行环境，**当** 用户按权威文档执行统一依赖安装命令，**则** 命令成功完成，并且文档无需要求用户先运行 `make`。
2. **给定** 依赖安装已完成且 `uploads/` 中存在一个有效数据包，**当** 用户执行统一本地全流程命令，**则** 系统按现有任务契约生成一个任务目录、规则结果和报告，且行为与变更前一致。
3. **给定** 环境中没有 GNU Make，**当** 用户按权威文档完成上述流程，**则** 不出现缺少 `make` 导致的阻断。

---

### 用户故事 2 - 贡献者用一致入口完成质量门禁（优先级：P1）

一名贡献者修改后端代码后，希望运行项目要求的质量检查。其可以在本地使用与其他维护者、文档和自动化入口相同的命令完成检查，并获得清晰的成功或失败结果，而无需记忆平台专用命令。

**优先级理由**：质量门禁是所有变更交付的硬性要求；统一入口可减少执行偏差。

**独立测试**：分别构造通过和未通过检查的代码状态，运行统一质量检查入口，比较退出结果和失败信息。

**验收场景**：

1. **给定** 通过质量要求的代码，**当** 用户执行统一代码风格检查命令，**则** 命令成功结束。
2. **给定** 通过质量要求的代码，**当** 用户执行统一测试命令，**则** 命令成功结束。
3. **给定** 存在风格或测试失败，**当** 用户执行对应统一命令，**则** 命令以非零结果结束，并显示足以定位问题的失败信息。

---

### 用户故事 3 - 维护者完成契约、前端客户端和单规则调试（优先级：P2）

一名维护者调整接口契约后，希望通过统一入口导出契约并重新生成前端 API 客户端；在调试巡检规则时，也希望只重跑指定规则，而不用学习 Make 变量语法或平台脚本差异。

**优先级理由**：这些是日常开发中的高频工作流，必须与基础流程一起保持一致，否则会出现新旧入口并行的混乱。

**独立测试**：使用现有样例数据执行契约导出、前端客户端生成和单规则重跑，验证产物、结果和错误提示。

**验收场景**：

1. **给定** 当前接口契约文件，**当** 用户执行统一契约导出命令，**则** 契约产物按既有契约语义更新。
2. **给定** 契约产物已更新，**当** 用户执行统一前端客户端生成命令，**则** 前端客户端按契约重新生成。
3. **给定** 任务数据已解压且规则代码有效，**当** 用户以该规则代码执行统一单规则重跑命令，**则** 只有目标规则执行并刷新对应结果。
4. **给定** 用户执行需要参数的命令但未提供参数，**当** 命令运行，**则** 系统展示缺失参数、可用用法和可选择的操作建议，而不是出现平台相关或含糊的报错。

---

### 用户故事 4 - 开发者通过统一入口启动前端与端到端流程（优先级：P3）

一名开发者希望启动前端开发服务或端到端检查。其仍使用统一构建入口发起这些工作流；前端和浏览器自身依赖保持在其必要生态内，但入口和文档不再分裂为多套项目级命令。

**优先级理由**：完整开发流程包含前端和端到端场景；若这些场景仍使用独立入口，会削弱归一效果。

**独立测试**：按统一入口执行前端依赖安装、前端开发启动、前端构建、端到端依赖安装和端到端检查，并确认既有行为不变。

**验收场景**：

1. **给定** 前端依赖未安装，**当** 用户执行统一前端依赖安装命令，**则** 前端开发所需依赖可用。
2. **给定** 前端依赖可用，**当** 用户执行统一前端开发服务命令，**则** 服务按既有配置启动并可通过文档给出的地址访问。
3. **给定** 前端代码可构建，**当** 用户执行统一前端构建命令，**则** 构建产物生成且无新增失败。
4. **给定** 端到端依赖可用，**当** 用户执行统一端到端检查命令，**则** 端到端测试按既有范围运行。

### 边界情况

- 当用户运行不存在的操作名称时，系统如何处理？
  系统必须返回非零结果、解释命令不存在，并列出可用操作或提示如何查看帮助。
- 当必需参数缺失或无效时会发生什么？
  系统必须返回明确错误、说明期望值，并展示该操作的用法；不得静默跳过。
- 当目标环境中没有 GNU Make 时会发生什么？
  后端、巡检和质量门禁工作流不得因此失败。
- 当目标环境中缺少前端依赖或浏览器运行时会发生什么？
  相关前端或端到端操作必须返回可操作的前置条件提示；不得影响后端巡检流程。
- 当 Makefile 和本地启动 shell 包装脚本被删除后，用户尝试使用旧入口时会发生什么？
  系统不再提供旧入口；权威文档必须只指向 `python build.py`，不得保留兼容路径。
- 当某个检查或构建步骤失败时会发生什么？
  命令必须以非零结果结束，并保留可定位的错误输出；不得掩盖失败或返回误导性的成功。

## 需求 *(必填)*

### 功能需求

- **FR-001**：项目必须提供唯一权威的根目录 Python 入口 `build.py`，并通过 `python build.py <操作> [参数]` 执行安装、检查、测试、运行、契约和前端相关工作流。
- **FR-002**：该权威入口必须基于官方 Python 运行时调用；后端入口和后端依赖安装不得要求用户额外安装 GNU Make、uv 或其他项目级包管理器。前端和端到端流程的前置依赖单独声明。
- **FR-003**：项目必须删除 Makefile 和现有仅用于本地启动的 shell 包装脚本；不得在迁移后保留这些入口作为推荐或兼容路径。部署环境所需的构建脚本可在后续功能中单独开发。
- **FR-004**：统一入口必须至少支持依赖安装、代码风格检查、单元测试、本地全流程巡检、单规则重跑、在线 API + Web 启动、契约导出、前端 API 客户端生成、前端依赖安装、前端开发服务、前端构建、端到端依赖安装和端到端检查。
- **FR-005**：通过 `python build.py` 暴露的同一操作在不同支持平台上的名称、参数语义、成功结果和失败结果必须一致。
- **FR-006**：需要用户输入的操作必须提供可用帮助；必需参数缺失、操作不存在或前置条件不满足时，必须返回非零结果和可操作信息。
- **FR-007**：权威文档、项目级交付说明和质量门禁指引必须只使用统一入口描述工作流；历史文档中的归档记录不需要改写。
- **FR-008**：迁移不得改变巡检执行、任务隔离、结果契约、报告内容或 API 契约的业务语义。
- **FR-009**：质量检查、测试、全流程巡检、单规则重跑、契约导出和前端客户端生成必须产生与既有工作流等价的产物或状态。
- **FR-010**：前端和端到端工作流必须由统一入口发起；不要求替换其自身运行生态所必需的依赖或工具。
- **FR-011**：迁移完成时，Makefile 和相关本地启动 shell 包装脚本不得继续存在，且没有任何权威流程或文档依赖这些旧入口。
- **FR-012**：在仅具备官方 Python 的干净环境中，统一入口必须能够完成依赖安装、代码风格检查、单元测试、本地全流程巡检和单规则重跑；不得因缺少 Make、uv、PowerShell 专用包装或 Unix shell 而失败。
- **FR-013**：`pyproject.toml` 必须声明直接依赖及其允许范围；`requirements-lock.txt` 必须记录精确传递依赖版本，并作为安装的唯一权威锁。统一入口的标准安装必须使用该锁文件，不得在安装时重新放宽解析依赖版本。
- **FR-014**：`build.py` 的标准安装必须使用官方 Python 标准能力创建或复用 `.venv`，并通过精确锁文件安装依赖；后续操作必须优先使用该环境执行。若现有 `.venv` 不满足标准环境要求，必须给出重建提示。
- **FR-015**：项目必须从活跃仓库中移除 uv 专用入口、配置、文档约定和 `uv.lock`；不得保留 uv 作为标准或可选依赖安装路径。

### 关键实体 *(如果功能涉及数据则填写)*

- **统一构建操作**：开发者可执行的一个工作流，包含用途、参数、前置条件、成功输出和失败行为。
- **构建前提**：某项操作运行前需要满足的运行环境或依赖状态，例如后端运行时、前端依赖或端到端浏览器依赖。
- **质量门禁**：变更交付前必须通过的检查集合，包含代码风格检查、测试和按变更范围要求的验证。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**：在仅安装官方 Python 且不安装 GNU Make、uv 或其他项目级包管理器的干净环境中，用户可 100% 完成精确锁定的后端依赖安装、本地全流程、代码风格检查和单元测试。
- **SC-002**：权威文档中的 100% 当前工作流示例都通过统一入口表达，且不再要求用户运行 `make`。
- **SC-003**：统一入口支持的 13 类现有工作流在迁移后保持与旧入口等价的产物或结果状态。
- **SC-004**：对于未知操作、缺失参数或前置条件缺失，用户在单次执行内获得可操作错误信息的比例达到 100%。
- **SC-005**：新成员首次按权威文档执行基础流程时，只需使用 `python build.py`，无需阅读 Makefile 或学习 Make 语法。
- **SC-006**：迁移后，运行本地全流程和单规则重跑生成的巡检结果与迁移前在相同输入、规则和配置下保持业务语义一致。

## 假设

- “统一使用 Python”指项目级构建、任务编排和质量门禁入口由官方 Python 运行时承载；后端入口和后端依赖安装只依赖 Python 自带能力。不要求移除前端生态或端到端测试生态自身需要的 Node/npm、浏览器或相关依赖。
- 既有 Makefile 中的工作流语义是迁移基线；本功能先保持行为等价，不借机修改巡检、任务、契约或报告行为。
- `pyproject.toml` 用于声明直接依赖和允许范围；`requirements-lock.txt` 用于精确锁定实际安装版本。uv 及其专用锁文件从当前活跃开发流程中移除。
- Windows、macOS 和 Linux 是需要降低差异的主要开发平台；平台支持程度以其声明的基础运行环境为准。
- 历史 Speckit 产物、历史计划和归档文档中的 `make` 示例视为历史记录，不纳入强制迁移范围。
- 本功能的范围边界是开发者工作流入口归一；不改变运行模式架构、部署形态或巡检核心调度行为。
- 现有 Makefile 和仅用于本地启动的 shell 包装脚本应在本次迁移中删除；部署环境所需的构建脚本可作为后续功能单独开发。
