# 研究：KPI 按需分类与动态口径配置

## 决策 1：动态配置权威来源

**决策**：分类、指标规则、公式、阈值、容量规则、展示规则和公共配置使用 SQLite 作为运行时权威来源；基础资源和预留单位继续使用 Git JSON。

**理由**：资源全集要求版本评审和离线维护；业务口径需要按需在线调整和审计。两者分离后既保留资源全集口径，又满足前台动态维护诉求。

**替代方案**：
- 继续以 Git JSON 为规则事实来源：无法满足前台动态维护需求。
- 在线编辑后写回 Git：不适合服务部署和并发编辑，也容易破坏版本评审边界。
- 全部配置进数据库：会把资源全集身份也变成在线状态，违反本功能对资源全集口径的保护。

## 决策 2：不迁移规则 JSON

**决策**：不提供规则 JSON 导入命令。动态规则配置从空状态开始；公共配置用数据库单行默认值初始化。

**理由**：当前部署环境中除 `common.json` 外规则 JSON 均为空，导入能力没有业务价值，反而增加迁移和回滚复杂度。

**替代方案**：
- 提供一次性导入命令：解决不存在的历史数据问题，成本大于收益。
- 自动读取空 JSON 并写入：会让运行时继续出现双源路径，增加退役风险。

## 决策 3：任务快照 v2

**决策**：新增快照 schema v2，包含完整 `base_metrics`、有效 `metrics`、有效规则、`classification_version` 和 `rule_config_version`。

**理由**：完整基础资源允许线索在历史任务中准确区分未分类和未登记；版本号支持审计与结果解释；有效规则保证重跑确定性。

**替代方案**：
- 快照只保存有效指标：历史任务无法区分“当时未登记”和“现在已登记但当时未分类”。
- 线索实时读取最新基础数据：会让历史线索随基础数据变化，破坏任务可追溯性。

## 决策 4：线索匹配策略

**决策**：按 NFKC、空白折叠和大小写归一化后的基础指标中英文名匹配 CSV 源列名；唯一匹配进入可分类状态，多匹配进入人工确认状态。

**理由**：与现有 KPI 名称匹配方式保持一致，避免引入新的匹配语言。

**替代方案**：
- 仅精确字符串匹配：误报过少但可用性差。
- 模糊搜索自动分类：存在错误归类风险，违反配置可追溯原则。

## 决策 5：公式能力边界

**决策**：首版只支持受控 ratio 公式，包含分子、分母、分母兜底输入和缩放系数；不提供任意表达式 DSL。

**理由**：现有执行器已有安全实现；受控结构可以完整校验引用和循环，避免任意表达式带来的执行和安全风险。

**替代方案**：
- 表达式引擎：灵活但引入解析、安全、错误提示和审计复杂度。
- 多段计算 pipeline：当前需求不需要，扩大快照和执行器契约。

## 决策 6：版本与审计模型

**决策**：分类继续使用既有分类修订和审计；其他动态配置使用全局 `rule_config_version`、单行修订表和统一审计表。

**理由**：分类已经是稳定契约；全局规则版本足以保证快照可解释性，避免为每张配置表维护复杂版本链。

**替代方案**：
- 每类配置独立版本：可精确追踪，但快照和前端需要展示更多版本，当前收益不足。
- 只审计不版本化：无法可靠解释任务快照对应的配置集合。

## 决策 7：API 版本

**决策**：新增配置和线索能力使用 `/api/v4`；既有 `/api/v3` 分类接口保持不变。

**理由**：快照来源从 Git 规则切换为数据库是配置语义变化，符合“破坏性变更进入新版本”的项目约束。

**替代方案**：
- 继续扩展 `/api/v3`：减少路径数量，但会改变既有资源页面的配置语义。
- `/api/v5`：没有额外兼容收益。

## 决策 8：错误与失败策略

**决策**：数据库不可用或动态配置无效时，新任务和全量重建失败；不回退规则 JSON。单条线索解析失败只跳过该线索并记录原因。

**理由**：回退会造成同一路径在不同环境产生不同口径，违反确定性原则；线索是展示能力，允许部分降级。

**替代方案**：
- 静默使用空配置：会隐藏配置错误并产生误导性巡检结果。
- 线索任一失败导致列表不可用：没有必要降低可用性。
