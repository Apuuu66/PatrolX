# 功能规格：KPI 按需分类与动态口径配置

**功能分支**：`015-kpi-dynamic-config`

**创建日期**：2026-09-19

**状态**：已实现

**输入**：用户描述：资源全集有 600 多个指标，分类工作量巨大；系统应按任务真实遇到的指标提供按需分类线索。分类、阈值、聚合指标等动态口径都应在前台完成。`deploy/data/kpi/rules/` 下除 `common.json` 外均为空，因此不做规则 JSON 迁移。功能按 7 个阶段完整交付。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 按任务线索完成按需分类（优先级：P1）

作为巡检运营人员，我希望任务执行后只看到当前数据包中真实出现的待确认 KPI 列，并把其中可归属的指标分类到呼叫、接口或媒体业务域，这样我不需要面对全量资源集逐条分类。

**优先级理由**：这是本功能最直接的业务价值，可以立即降低 600 多个指标带来的分类压力。

**独立测试**：上传包含未分类 KPI 列的数据包并执行巡检，任务详情应出现按需分类线索；用户完成分类后返回任务详情并手动重跑相关 KPI 规则，规则结果应按新分类重算。

**验收场景**：

1. **给定** 一个 KPI 数据包包含当前未分类的基础指标列，**当** 任务完成巡检，**则** 任务详情展示这些列的源名称、来源文件、记录数和样例值。
2. **给定** 某条线索可以唯一匹配基础指标，**当** 用户进入分类页面，**则** 系统按线索预置搜索条件，用户可以找到并选择对应指标。
3. **给定** 用户已完成分类，**当** 用户返回任务详情，**则** 系统提示手动重跑相关 KPI 规则，且不自动触发重跑。
4. **给定** 用户手动重跑相关规则，**当** 重跑完成，**则** 只有目标 KPI 规则结果更新，其他规则结果保持不变。
5. **给定** 某条线索无法匹配任何基础指标，**当** 用户查看线索，**则** 系统明确显示该列未登记，并提示只能通过离线资源全集更新，不允许在线新增指标。

---

### 用户故事 2 - 在线维护聚合指标与公式（优先级：P1）

作为 KPI 口径维护人员，我希望在基础指标配置页面为 raw 指标设置聚合方式，并为派生指标配置受控公式，这样后续任务可以使用最新业务口径。

**优先级理由**：聚合和公式决定 KPI 的计算口径，是与分类同等重要的动态配置。

**独立测试**：为已有基础指标修改聚合方式或 ratio 公式，保存成功后创建新任务；新任务快照应使用新口径，旧任务单规则重跑仍使用旧快照。

**验收场景**：

1. **给定** 一个已分类的 raw 指标，**当** 用户选择受支持的聚合方式并保存，**则** 系统保存指标规则、记录审计并递增规则配置版本。
2. **给定** 三个已分类的基础指标构成比率关系，**当** 用户配置分子、分母和缩放系数，**则** 新任务按公式计算派生指标。
3. **给定** 公式引用不存在、被删除或形成循环的指标，**当** 用户保存，**则** 系统拒绝保存并说明原因。
4. **给定** 某指标已被公式引用，**当** 用户尝试修改其业务域，**则** 系统拒绝并说明引用保护。
5. **给定** 一个使用旧配置的历史任务，**当** 用户单规则重跑，**则** 系统复用该任务的既有快照，不使用最新公式。

---

### 用户故事 3 - 在线维护阈值（优先级：P1）

作为 KPI 口径维护人员，我希望按业务域和指标配置默认阈值与 5/15/30/60 分钟周期阈值，这样巡检判断不需要修改代码或 Git 配置文件。

**优先级理由**：阈值是巡检结论的核心输入，必须支持随客户和版本动态调整。

**独立测试**：新增或修改某业务域指标阈值，创建新任务后确认判断使用新阈值；单规则重跑旧任务仍使用旧阈值。

**验收场景**：

1. **给定** 一个已分类指标，**当** 用户创建最小值或最大值阈值并保存，**则** 系统保存阈值、记录审计并递增规则配置版本。
2. **给定** 同一业务域和指标已有阈值，**当** 用户再次创建，**则** 系统拒绝重复配置。
3. **给定** 用户配置一个或多个周期阈值，**当** 新任务执行，**则** 对应周期使用周期阈值，其他周期使用默认阈值。
4. **给定** 指标已被阈值引用，**当** 用户尝试重新分类该指标，**则** 系统拒绝并提示引用保护。
5. **给定** 用户删除阈值，**当** 创建新任务，**则** 新任务不再应用该阈值，历史结果保持不变。

---

### 用户故事 4 - 在线维护容量、展示和公共配置（优先级：P2）

作为 KPI 配置管理员，我希望统一维护容量列映射、展示规则、输入时区和解析预算，这样完整 KPI 配置不再依赖 Git 规则文件。

**优先级理由**：这些配置共同构成完整运行时口径，但调整频率低于分类、公式和阈值。

**独立测试**：分别修改容量规则、展示规则和公共配置，创建新任务后确认快照包含全部修改；旧任务重跑行为保持稳定。

**验收场景**：

1. **给定** 一个容量源列，**当** 用户映射到基础指标并设置容量语义，**则** 新任务按该映射识别容量数据。
2. **给定** 一个业务域指标，**当** 用户设置展示角色，**则** 前端和报告按新角色展示。
3. **给定** 用户修改输入时区或解析预算，**当** 新任务执行，**则** 快照和新任务行为使用新配置。
4. **给定** 容量或展示规则引用基础指标，**当** 该指标被移除或重新分类，**则** 系统执行引用保护或明确拒绝。

---

### 用户故事 5 - 查看配置审计与版本（优先级：P1）

作为配置管理员，我希望查看每一次分类和规则配置变更的操作人、前后状态和时间，这样可以追溯某个任务为什么使用当时口径。

**优先级理由**：动态配置必须有可追溯性，否则巡检结果难以解释和回滚。

**独立测试**：连续执行分类、公式、阈值和其他配置修改，然后查看审计；每条成功修改都有记录，失败修改没有部分写入。

**验收场景**：

1. **给定** 用户成功修改任一 KPI 动态配置，**当** 查看审计，**则** 审计包含操作类型、操作人、变更前后内容、结果和 UTC 时间。
2. **给定** 一次保存因校验失败被拒绝，**当** 查看配置和审计，**则** 配置不变，不产生成功审计。
3. **给定** 多次配置变更，**当** 查看规则配置版本，**则** 每次成功变更递增一次。
4. **给定** 任务快照，**当** 用户查看详情，**则** 快照包含生成时的分类版本和规则配置版本。

---

### 用户故事 6 - 退役 Git 规则文件（优先级：P2）

作为系统维护人员，我希望运行时只使用数据库动态配置，避免 Git 规则文件和数据库配置产生双源冲突。

**优先级理由**：动态配置必须有唯一事实来源；保留双源会造成解释困难和维护风险。

**独立测试**：在规则文件目录不存在或被清空的情况下启动系统并执行任务，确认任务只使用数据库配置；基础资源文件仍正常加载。

**验收场景**：

1. **给定** 数据库配置已可用，**当** 生成任务快照，**则** 系统不读取 `rules/common.json`、`metric-rules.json`、`thresholds.json`、`capacity-rules.json` 和 `display-rules.json`。
2. **给定** 本地模式和在线模式，**当** 执行相同数据包和相同配置，**则** 两者生成一致的 KPI 判定逻辑。
3. **给定** 基础资源 Git 文件存在，**当** 任务执行，**则** 系统继续使用资源 ID、稳定 key 和中英文名。
4. **给定** 旧任务包含旧版快照，**当** 查看或单规则重跑，**则** 系统按旧快照兼容执行，不要求迁移旧规则文件。

---

### 边界情况

- 当线索匹配到多个基础指标时，系统必须返回待人工确认状态，不得自动分类。
- 当线索来自历史任务且当前基础数据已变化时，系统必须依据任务快照中的基础指标解释线索。
- 当基础指标被离线工具移除，但数据库公式、阈值、容量或展示规则仍引用它时，离线工具必须拒绝替换基础数据。
- 当公式、阈值、容量或展示规则引用未分类指标时，保存可以成功，但生成新快照和执行时不得静默生效；用户界面必须提示配置未生效原因。
- 当多个用户同时修改配置时，系统必须保证单次保存原子提交，成功后版本只递增一次。
- 当任务执行过程中配置变化时，当前任务必须继续使用已生成快照。
- 当配置数据库不可用时，新任务不能静默使用空规则或 Git 规则文件，必须失败并说明原因。
- 当公共配置非法，例如时区不存在或预算小于等于零，系统必须拒绝保存并保持旧配置。
- 当单条 KPI 文件解析失败时，任务仍遵循既有容错契约，不得中断整个任务。
- 当没有任何待分类线索时，任务详情不得展示空线索入口。

## 需求 *(必填)*

### 功能需求

- **FR-001**：系统必须从任务 KPI 规则结果中提取真实出现的未识别列，形成按需分类线索。
- **FR-002**：系统必须对线索区分未分类、已分类待重跑、未登记和匹配不明确四种状态。
- **FR-003**：用户必须能够从未分类线索进入基础指标分类页面，并按源列名预置搜索。
- **FR-004**：系统必须继续支持单个或批量将基础指标分类到 `call`、`api` 或 `media`。
- **FR-005**：系统必须保留基础指标资源 ID、稳定 key、中文名、英文名和单位信息作为离线登记的 Git 基础数据。
- **FR-006**：系统必须禁止通过在线分类、公式、阈值、容量或展示配置新增、修改或删除基础指标资源。
- **FR-007**：系统必须支持在线维护 raw 指标的聚合方式。
- **FR-008**：系统必须支持在线维护受控 ratio 派生公式，包括分子、分母、分母兜底输入和缩放系数。
- **FR-009**：系统必须支持在线维护业务域阈值和 5/15/30/60 分钟周期阈值。
- **FR-010**：系统必须支持在线维护容量规则、展示规则和公共配置。
- **FR-011**：系统必须对动态配置保存执行完整引用校验、唯一性校验和取值校验。
- **FR-012**：系统必须保证单次配置保存原子生效，失败时不产生部分配置或部分审计。
- **FR-013**：系统必须为每次成功的动态配置变更写入操作人、操作类型、变更前后内容、结果和 UTC 时间。
- **FR-014**：系统必须维护分类版本和规则配置版本，并在任务快照中记录生成时版本。
- **FR-015**：系统必须在任务执行或全量重建时生成不可变 KPI 快照；普通 KPI 规则只能读取任务快照。
- **FR-016**：单规则重跑必须优先复用既有任务快照，不得因配置变化而隐式重建快照。
- **FR-017**：增量重建必须保持既有快照不变；全量重建必须按当前分类和规则配置生成新快照。
- **FR-018**：系统必须禁止重新分类已被公式、阈值、容量规则或展示规则引用的指标。
- **FR-019**：离线资源全集更新必须保护数据库中仍引用的基础指标；被引用指标被移除时必须整体失败。
- **FR-020**：运行时不得读取或依赖 KPI 规则 JSON 文件；KPI 规则 JSON 只能作为过渡期备份，最终退役。
- **FR-021**：本地模式和在线模式必须使用同一套动态配置、快照生成和 KPI 巡检逻辑。
- **FR-022**：系统必须在配置数据库不可用或配置无效时让新任务失败，不得静默跳过 KPI 或回退到规则 JSON。
- **FR-023**：前端必须提供基础指标与分类、按需线索、聚合与公式、阈值、容量规则、展示规则、公共配置和审计的统一配置入口。
- **FR-024**：前端分类状态色必须继续遵循 `pass` 绿、`warn` 黄、`fail` 红、`error` 灰、`skip` 蓝的既有约定。
- **FR-025**：所有公开接口契约必须进入 OpenAPI，并由生成的客户端调用。

### 关键实体 *(如果功能涉及数据则填写)*

- **基础资源指标**：离线登记的资源全集成员，包含资源 ID、稳定 key、中文名、英文名和单位预留信息；只能由离线工具维护。
- **分类状态**：基础指标与业务域的当前归属，可为未分类；支持审计和版本追踪。
- **指标规则**：基础指标的计算口径，包含类型、语义分组、展示角色、单位、聚合方式；派生指标额外包含公式。
- **公式**：受控比率定义，包含分子、分母、分母兜底输入和缩放系数。
- **阈值**：业务域内指标的判断方向、默认值和周期阈值。
- **容量规则**：源列与容量指标、容量语义、确认状态的映射。
- **展示规则**：业务域内指标的展示角色。
- **公共配置**：输入时区和文件、记录解析预算。
- **规则配置审计**：动态配置变更的可追溯记录。
- **任务 KPI 快照**：任务生成时的基础资源、有效分类、有效规则配置和版本号集合。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**：面对包含 600 多个资源指标的完整资源集，用户只需要处理当前任务线索中出现的指标即可完成一次按需分类闭环。
- **SC-002**：一次任务线索列表能在 2 秒内完成加载；当线索超过 100 条时必须支持分页或明确折叠。
- **SC-003**：任意一次配置保存要么完整成功，要么完整失败；不存在用户可见的部分保存状态。
- **SC-004**：每个成功配置修改都能在审计中找到唯一记录，且规则配置版本递增 1。
- **SC-005**：使用相同数据包、相同基础数据版本、相同分类版本和相同规则配置版本重跑，KPI 判定结果保持一致。
- **SC-006**：修改动态配置后，旧任务单规则重跑结果保持基于旧快照；全量重建结果基于新快照。
- **SC-007**：本地模式和在线模式对同一数据包和同一快照生成一致的 KPI 结果。
- **SC-008**：功能完成后，运行时不再依赖任何 `rules/*.json` 文件。

## 假设

- 当前部署环境中的 KPI 规则 JSON 除 `common.json` 外均为空，因此不需要把历史规则 JSON 导入数据库。
- 现有基础指标和预留单位继续由离线 CSV 工具生成并提交 Git。
- 现有分类能力继续保留，但需要在完整配置中心中呈现。
- 公式首版只支持当前执行器已支持的受控 ratio，不提供任意表达式语言。
- 桌面端是唯一前端形态，不做移动端适配。
- 本功能通过新的 API 版本承载破坏性配置来源变化，避免改变既有 `/api/v3` 字段含义。
- 历史任务快照必须兼容读取；不提供把旧任务重写到新快照的自动迁移。

## 澄清结论

- 不执行 `rules/*.json` 到数据库的历史迁移；除 `common.json` 中的默认公共配置外，动态规则配置从空状态开始。
- 新配置契约使用 `/api/v4`；既有 `/api/v3` 分类接口语义不改变。
- 分类后的重跑始终由用户手动触发；系统不得自动重跑任务或规则。
- 任务线索必须依据任务生成时的基础数据快照解释，不能用最新基础数据改写历史任务语义。
- 派生公式首版只支持受控 ratio；任意表达式 DSL 不在范围内。
- 基础资源只能通过离线 CSV 工具更新；在线配置只能引用已有基础资源。
- `rules/*.json` 只允许作为过渡期备份存在；功能完成时运行时不得读取。
