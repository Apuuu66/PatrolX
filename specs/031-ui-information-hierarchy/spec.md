# 功能规格：主界面信息层级重构（巡检控制台方向）

**功能分支**：`031-ui-information-hierarchy`

**创建日期**：2026-10-10

**状态**：已澄清

**输入**：用户描述："界面上内容总感觉很乱，没有主次"（范围：所有主页面）。经 OpenDesign 设计探索，用户于 2026-10-10 确认采用"B 巡检控制台为主 + C 简化管理台为辅 + A 保守优化视觉基线"的组合方向。

## 背景

当前前端（React + TypeScript + Vite + Ant Design + ECharts）把系统能力都平铺到了界面上，主要问题不是缺功能，而是缺层级：

- **任务列表**：每张卡片用等权重的五色状态块表达 pass/warn/fail/error/skip，0 值也占同样的视觉位置；任务 ID、元数据、时间、准备状态与操作混杂，第一眼看不出"哪个任务有问题"。
- **任务详情**：顶部同时出现 4 个概览大数字与 5 个状态统计块；黄色的"重点关注"提示条与下方规则表格表达同一件事；执行信息、任务信息、技术字段散落在多张卡片里，主次不清。
- **规则详情**：标题、结论、建议、发现、度量单元、指标表、技术信息按顺序平铺，首屏无法直接回答"结论是什么、要不要处理"。
- **其余页面**（设备台账、设备详情、基础指标、规则管理、数据字典、报告、日志、用户管理）各自成型，缺少统一的页头、状态、操作与间距基线。

本轮是 2026-09 ~ 2026-10 两轮 OpenDesign 设计探索的落地版本。探索产出的三个方向原型（A 保守优化 / B 巡检控制台 / C 简化管理台）基于同一套真实任务与规则数据，覆盖任务列表、任务详情、规则详情三个页面；本轮按用户确认的组合方向重构生产前端。

**本轮边界**：

- 只改前端展示层，不改变后端规则、执行器、数据模型与 OpenAPI 契约；不新增接口。
- 数据来源不变：完全使用既有接口返回的字段推导展示结论。
- 不改变路由结构与 URL 语义，既有深链保持可用。

## Clarifications

### Session 2026-10-10

- Q: 设计探索产生的三个方向如何取舍？ → A: 采用"B 巡检控制台为主 + C 简化管理台为辅 + A 保守优化视觉基线"：任务列表与规则表用 B 的密度与对齐，任务详情首屏用 C 的结论优先，视觉样式走 A 的克制 AntD 基线。
- Q: 其余主页面（设备台账 / 设备详情 / 基础指标 / 规则管理 / 数据字典 / 报告 / 日志 / 用户管理）本轮做到什么程度？ → A: 只统一视觉基线（页头结构、字号间距、卡片、状态标签、操作分组、空 / 加载 / 错误态），不重排信息架构；结构性重排留待后续独立版本，避免一次性放大验收面。
- Q: 任务列表是否保留卡片形态？ → A: 不保留。列表统一为单表行式列表一种形态，异常置顶。
- Q: 任务列表默认排序如何确定？ → A: 默认异常优先（fail / error 置顶），同状态内按创建时间倒序；本轮不新增排序切换控件。
- Q: 本轮是否需要向代表性样例包新增数据？ → A: 不需要。本轮不引入新数据语义，展示效果用例复用既有代表性样例包与 E2E 种子任务即可复现。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 值班人员在任务列表一眼找到要处理的任务（优先级：P1）

值班人员打开平台首页，不需要逐个阅读任务卡片：异常任务排在最前并给出失败原因摘要；正常任务只保留必要信息。他能在一屏内判断"今天有没有要处理的包"。

**优先级理由**：任务列表是所有用户的入口页面，直接决定"第一眼看什么"。当前五色等权状态块正是"乱"的最主要来源。

**独立测试**：用现有 E2E 种子任务（含 1 个主包解压失败任务、3 个完成任务）打开任务列表，检查异常任务是否置顶、是否显示失败原因、准确展示状态摘要与元数据。

**验收场景**：

1. **给定** 任务列表中存在 1 个失败任务与 3 个完成任务，**当** 打开任务列表，**则** 失败任务排在第一行，行内直接可见失败原因摘要，无需展开。
2. **给定** 某任务所有规则均通过，**当** 查看该任务行，**则** 状态摘要只表达"通过 1"这类非零信息，不出现多组彩色 0 值数字。
3. **给定** 用户想查看失败详情，**当** 在失败任务行点击"失败日志"，**则** 直接进入该任务的日志页且失败原因可见（不超过 2 次点击）。
4. **给定** 用户需要重跑或删除任务，**当** 打开该行的更多操作，**则** 低频与危险操作从主操作中分离，删除仍需二次确认。

---

### 用户故事 2 - 打开任务详情，首屏就知道"有没有问题、下一步做什么"（优先级：P1）

值班人员从列表点进任务详情，首屏是结论区：结论标签、一句话结论、状态计数、主操作和任务关键元数据；需要证据时向下看"重点关注"与全部规则。

**优先级理由**：详情页是排查主战场，当前"4 大数字 + 5 状态块 + 重复提示条"让用户第一眼看不到结论，才会觉得"乱"。

**独立测试**：用含 4 条失败、2 条告警的真实种子任务打开详情页，检查首屏结论区内容；再验证全通过任务与失败任务的结论差异。

**验收场景**：

1. **给定** 某任务 13 条规则中 4 条失败、2 条告警，**当** 打开任务详情，**则** 首屏结论显示"需要关注"，并给出一句话结论与失败/告警数量。
2. **给定** 某任务全部规则通过，**当** 打开任务详情，**则** 结论显示"全部通过"，不使用失败红高权重表达。
3. **给定** 某任务主包解压失败，**当** 打开任务详情，**则** 结论区显示失败原因与失败阶段，并可跳转失败日志；规则区不展示伪造的规则结果。
4. **给定** 用户在结论区点击"查看报告"，**当** 报告可用，**则** 直接进入或下载报告；任务执行中时该操作不可用且原因可见。

---

### 用户故事 3 - 规则详情按"结论 → 证据 → 建议"阅读（优先级：P2）

排查人员从任务详情进入某条规则，先看到结论与建议，再看发现列表与指标证据；技术字段默认收起。

**优先级理由**：规则详情是排查闭环的最后一跳，当前平铺结构让用户在指标表与技术字段里"找结论"。

**独立测试**：用 `kpi.measurement_units`（全通过）与失败规则分别打开规则详情，检查结论、建议、证据顺序与跳过原因展示。

**验收场景**：

1. **给定** 任意规则结果，**当** 打开规则详情，**则** 首屏可见规则状态、结论摘要与建议。
2. **给定** 规则因无匹配文件被跳过，**当** 打开规则详情，**则** 跳过原因 `skip_reason` 可见。
3. **给定** 用户需要看指标明细，**当** 切换"显示全部列"，**则** 精简列与全部列之间可切换，默认精简。
4. **给定** 用户在规则详情点击"重跑规则"，**当** 重跑进行中，**则** 按钮呈进行中状态，完成后本页结果刷新。

---

### 用户故事 4 - 其余主页面不再"各写各的"（优先级：P3）

设备台账、设备详情、基础指标、规则管理、数据字典、报告、日志、用户管理页面套用统一视觉基线后，用户在不同页面之间切换时不需要重新适应字号、间距、状态标签与操作位置。

**优先级理由**：用户反馈"都乱"，只改 3 个页面无法解决跨页面的一致性问题；但其余页面各有既定功能，本轮只统一表达方式，不重排信息架构。

**独立测试**：逐页走查基线清单（页头结构、状态标签、操作分组、空/加载/错误态、间距与字号），至少对其中 1 个页面补充 E2E 断言。

**验收场景**：

1. **给定** 用户从任务列表进入设备台账或基础指标页面，**当** 浏览页面，**则** 页头、间距、卡片样式与状态标签与任务页保持同一基线。
2. **给定** 某页面数据加载失败，**当** 查看页面，**则** 错误态提供统一的重试入口与文案风格。
3. **给定** 某页面列表为空，**当** 查看页面，**则** 空状态给出统一说明与下一步动作。

---

### 边界情况

- 任务列表为空（尚未上传任何包）时，空状态必须保留"上传数据包"主入口。
- 全部任务均正常时，概览条不得出现"需要处理"的高权重提示。
- 任务处于排队中 / 执行中时，结论区与行操作必须反映进行中状态，禁用不可用操作并说明原因。
- 主包解压失败的任务只有失败阶段与原因，没有规则结果，不得展示空规则表格冒充结果。
- 只有告警（无失败）的任务，结论用"需要关注"但不得使用失败红。
- 规则被跳过时跳过原因必须可见，不允许静默通过。
- 任务名、规则名、文件路径超长时截断展示且不破坏布局，完整值仍可获取。
- 规则数量多（13 条以上）时，分组折叠与筛选不得造成信息丢失。
- 1280px 宽度下不得出现横向滚动条；1920px 下内容不应被无限拉伸。
- 单规则重跑进行中时，页面其他区域保持可读，不得整页跳动。
- 数据加载中必须使用骨架屏；局部刷新不得引起整页骨架抖动。

## 需求 *(必填)*

### 全局视觉基线

- **FR-001**：系统必须使用统一的视觉基线表达字号层级（页面标题 / 区块标题 / 正文 / 次要说明）、间距、卡片、分隔线与圆角，并把基线写入 `docs/design/DESIGN.md` 作为长期约束。
- **FR-002**：状态色与语义必须全站一致（通过绿 / 告警黄 / 失败红 / 异常灰 / 跳过蓝），且必须同时提供文字标签，不得只依赖颜色。
- **FR-003**：0 值状态不得使用与非零状态相同的视觉权重。
- **FR-004**：每个页面最多保留 1 个主操作；低频操作与危险操作必须收进次要入口，危险操作仍需二次确认。
- **FR-005**：技术信息（任务 ID、规则编码、文件路径、原始字段）必须弱化展示或默认折叠，可按需展开与复制。

### 任务列表

- **FR-006**：任务列表必须以单表面、列对齐的行式列表呈现，每行一个任务；行内信息顺序为"任务名与状态 → 非零状态摘要 → 元数据 → 时间与耗时 → 操作"。
- **FR-007**：失败与异常任务必须默认排在最前并以状态色标出；同状态内按创建时间倒序排列。
- **FR-008**：失败与异常任务行必须直接给出原因摘要（例如主包解压失败），并提供进入失败日志的入口。
- **FR-009**：任务状态必须用"分布条 + 非零计数"表达；全为 0 的状态不得逐项占位。
- **FR-010**：列表页顶部概览必须是一条概览条（任务总量 + 状态分布 + 注册规则 / 规则结果 / 发现问题数），不得同时出现多组等权重数字。
- **FR-011**：列表必须表达每个任务的数据准备状态；存在问题时必须能看到问题摘要并触发重试，不得隐藏。
- **FR-012**：行主操作为"详情"；次要操作为"报告"与"失败日志"；重跑、增量重建、全量重建、删除必须收进更多菜单。
- **FR-013**：任务状态筛选、搜索与分页必须保持可用；默认分页大小保持 10 条。

### 任务详情

- **FR-014**：任务详情首屏必须呈现结论区：结论标签、一句话结论、状态计数、主操作与任务关键元数据（数据包、版本、设备、省份、运营商、网元类型、时间与耗时）。
- **FR-015**：结论必须覆盖这些形态——全部通过 / 需要关注（给出失败与告警数量）/ 任务失败（给出原因）/ 执行中 / 排队中。
- **FR-016**："重点关注"必须默认可见并以列表呈现，按失败 → 告警排序；同一信息不得在提示条与列表之间重复表达。
- **FR-017**：全部规则必须支持按类别分组与折叠，默认展开存在异常的分组。
- **FR-018**：执行信息与技术信息必须默认折叠，展开后可查看完整字段。
- **FR-019**：任务失败时必须展示失败原因与失败阶段，并提供跳转失败日志的入口。

### 规则详情

- **FR-020**：规则详情必须按"结论 → 建议 → 源文件匹配 → 发现 → 度量与指标证据 → 技术信息"的顺序组织；首屏必须可见结论与建议。
- **FR-021**：规则状态为跳过时必须展示跳过原因。
- **FR-022**：指标证据必须支持"精简列 / 全部列"切换，默认精简。
- **FR-023**：单规则重跑入口必须在首屏可及，重跑进行中状态可见，完成后仅刷新本页结果。

### 其余主页面

- **FR-024**：设备台账、设备详情、基础指标、规则管理、数据字典、报告、日志、用户管理页面必须套用统一基线（页头结构、卡片、状态标签、操作分组、空 / 加载 / 错误态），不得保留与基线冲突的独立样式。
- **FR-025**：上述页面在本轮只统一视觉基线，不得重排信息架构或改变功能语义；结构性重排属于后续独立版本。

### 兼容与约束

- **FR-026**：既有交互行为必须保持：状态筛选、搜索、分页、轮询、详情页标签与续跑状态、单规则重跑、报告查看、删除与重建确认。
- **FR-027**：不得新增或修改 OpenAPI 契约字段；若展示确需新数据，必须先在 `docs/api/openapi.yaml` 增加契约并同步生成客户端后才可实现。
- **FR-028**：桌面优先，必须保证 1280px ~ 1920px 宽度区间可用；不新增移动端适配。
- **FR-029**：不得引入新的 UI 组件库；沿用现有 React + TypeScript + Vite + Ant Design + ECharts 技术体系。
- **FR-030**：既有自动化测试必须继续通过；因界面结构调整导致的选择器变化必须等价替换断言，不得删除对既有行为的覆盖。

### 关键实体 *(如果功能涉及数据则填写)*

本功能不引入新的契约数据实体；涉及以下展示对象：

- **任务行视图**：任务名、任务状态、非零状态计数与分布、元数据（省份 / 运营商 / 网元类型 / 版本 / 设备 ID）、创建时间与耗时、数据准备状态、操作集合。
- **任务结论**：由任务状态与规则状态计数推导的结论标签、一句话结论与下一步动作。
- **规则关注项**：规则名称、编码、状态、严重度、结论摘要、耗时与可用操作。
- **视觉基线**：字号层级、间距刻度、卡片与分隔线、状态语义色、操作分层规则，作为 `docs/design/DESIGN.md` 的长期约束。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**：在 1440×900 视口下，任务列表首屏同时可见概览条与全部 4 条种子任务，无横向滚动。
- **SC-002**：在 1440×900 视口下，任务详情首屏（不滚动）同时可见结论标签、一句话结论、状态计数、主操作与关键元数据。
- **SC-003**：失败任务在任务列表中位于第一行，且其失败原因摘要在行内直接可见；从该行进入失败日志不超过 2 次点击。
- **SC-004**：从任务列表出发，到达任一条失败规则的详情页不超过 3 次点击。
- **SC-005**：任务详情中同一事实（例如失败规则条数）不得出现两处及以上等权重复表达。
- **SC-006**：其余主页面逐页走查通过统一基线清单（页头、状态、操作分组、空 / 加载 / 错误态），且至少 1 个页面有自动化断言。
- **SC-007**：前端单元测试、构建与端到端测试全部通过；展示效果以真实样例包在界面中可复现并留存截图证据。

## 假设

- 用户是运维与巡检人员，桌面环境使用，习惯 Ant Design 交互模式；不要求移动端。
- 视觉方向以 OpenDesign 探索结论为准：列表与规则表采用 B 的密度与对齐，任务详情首屏采用 C 的结论优先，样式走 A 的克制 AntD 基线。
- 本轮不改变路由与 URL 语义，既有深链（任务详情、规则详情、报告、日志）继续可用。
- 本轮不新增数据语义，因此代表性样例包（`ZZapp01BCN_app_Problem_scene_333.zip`）不需要新增数据；展示效果用例复用既有样例与 E2E 种子任务复现。
- 状态色沿用 `docs/design/DESIGN.md` 现有定义，不新增状态语义。
- 其余主页面若需要结构性重排，属于后续独立版本，不在本轮范围。
