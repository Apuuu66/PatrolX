# 阶段 0 研究：设备台账维护与网元类型命名

## 1. 删除语义

**Decision**：按用户确认使用物理删除。删除设备时同步删除 `inventory_devices` 中该设备、`inventory_observations` 中该设备观测和该设备历史审计；随后写入一条删除审计。任务原始包、任务目录、任务详情和 `inventory.json` 不修改。

**Rationale**：用户明确要求“删除就全部删除”。物理删除避免隐藏记录和重复身份误判；管理员确认弹窗和删除审计提供操作安全边界。

**Alternatives considered**：

- 软删除：可以恢复历史，但与用户确认冲突。
- 只删设备不删观测：会留下悬挂外键和不可见观测。
- 修改任务 `inventory.json`：违反任务产物只读约束。

## 2. 台账数据归属

**Decision**：继续使用 `InventoryDevice` 台账档案，不新增草稿表或设备别名表；维护能力只保留物理删除。

**Rationale**：设备身份由省份和规范化设备名确定；档案必须由任务解析创建，避免手动身份与巡检身份不一致。

**Alternatives considered**：

- 手动新增：会造成身份来源不一致，已裁剪。
- 草稿表：用户没有要求草稿流程。
- 允许修改设备名或省份：会改变 `device_id`，破坏历史关联。

## 3. API 与契约版本

**Decision**：在现有 `/api/v2/inventory/devices/{device_id}` 资源上只保留 `DELETE`；移除 `POST` 和 `PATCH` 契约入口。

**Rationale**：用户确认台账维护只保留删除；沿用资源路径可保持查询客户端和删除调用一致。写接口要求 admin，与既有管理接口一致。

**Alternatives considered**：

- 新增 v6：成本高，对同资源写操作没有兼容收益。
- 使用 `PUT /devices/{id}/soft-delete`：与物理删除语义不一致。
- 用查询参数控制删除范围：前端已确认即可，后端不需要额外开关。

## 4. 权限与审计

**Decision**：台账删除要求 `admin`，并写删除审计；先收集被删数据摘要，再在事务内删除并落审计。

**Rationale**：物理删除风险高，必须能回答“谁在什么时候删除了哪台设备”。审计不用于恢复数据，但保留操作责任链。

**Alternatives considered**：

- 允许普通用户删除：高风险操作与当前权限模型不符。
- 不记录审计：无法追踪高风险删除。
- 把审计写入文件：事务一致性和查询能力弱于 SQLite。

## 5. 网元类型文案

**Decision**：只调整用户可见中文文案，后端字段继续叫 `product`，字典键继续叫 `product`。

**Rationale**：字段名是契约和历史数据身份，不应该因展示语义调整而变更。新增 API 版本或迁移字段会带来不必要的兼容风险。

**Alternatives considered**：

- 字段改为 `network_element_type`：破坏既有契约。
- 只改上传表单：会造成任务元数据、数据字典和上传页文案不一致。

## 6. 网元类型与多设备解析

**Decision**：将 `LST ME.txt` 解析从“整文件一个设备”升级为“记录级设备解析”。一条记录由设备名行开启，后续字段归属该记录；每条记录解析设备名、网元类型和版本。上传 `product` 作为“网元类型”筛选条件，只归档规范化后相等的记录。

**Rationale**：用户明确说明网元类型是 `LST ME.txt` 里的行级关键属性，一个包可能有多台设备。继续聚合整个文件会把多设备误判为身份冲突，也无法表达筛选范围。`product` 字段名保持不变，避免契约破坏。

**Alternatives considered**：

- 继续要求单设备文件：不满足真实包中多设备的现状。
- 保留多设备但全部归档：违背“只关注网元类型相等记录”的要求。
- 新增 `network_element_type` API 字段：字段语义与既有 `product` 重复，增加版本和前端迁移成本。

**Consequences**：`parser_version` 升级为 `2`；任务证据新增记录摘要；台账归档器必须支持一个任务多条设备观测。旧任务证据继续按旧展示逻辑读取。
