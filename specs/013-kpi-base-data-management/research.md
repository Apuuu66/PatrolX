# 研究结论：KPI 基础数据管理

## 1. 现状

- 当前权威配置是单一 `deploy/data/kpi_catalog.json`，由 `app/inspectors/kpi/catalog.py::load_kpi_catalog()` 加载。
- 配置内部已经区分基础指标、预留单位、通用规则、指标规则、阈值、容量规则和展示规则，但都聚合在一个 JSON 文件内。
- 离线工具 `python -m app.tools.kpi_catalog generate` 会从资源 CSV 全量生成基础指标和预留单位，并读取既有文件中的规则后整体回写。
- 任务启动或首次需要 KPI 配置时，服务会把 Git 配置和 SQLite 分类状态组合成有效目录，并写入 `output/<task_id>/kpi/kpi_catalog_snapshot.json`。
- 已有任务重跑会优先复用既有快照；当前全量重跑在快照缺失时仍可能补写，指定规则重跑也通过同一服务读取或补写。

## 2. 配置拆分方案

### 结论

采用“按类型拆分为固定文件集”的方案：

```text
deploy/data/kpi/
  base/
    metrics.json
    units.json

  rules/
    common.json
    metric-rules.json
    thresholds.json
    capacity-rules.json
    display-rules.json
```

不引入额外的 manifest 文件。目录和文件名就是类型边界；每个 JSON 使用严格 Schema 校验，跨文件引用在目录聚合时统一校验。

### 理由

- 基础指标与规则是不同变更频率、不同维护责任的数据；拆分后离线导入不会触碰规则文件。
- 固定文件集比 manifest + 动态文件更简单，符合当前配置规模。
- 每个文件保持确定性 JSON 格式，便于 Git 审查和避免生成器重排造成无意义 diff。
- 现有加载器和快照结构可以保留，只需要把输入从单文件改为目录聚合，避免影响任务结果契约。

### 被否决方案

- **继续使用单一 JSON**：实现最小，但资源 CSV 刷新与人工规则维护边界不清。
- **每类数据一个目录 + manifest**：扩展性更强，但当前固定七类数据不需要动态发现，manifest 会增加一致性问题。
- **拆分成更多小文件**：当前类型已经足够表达用户关注的维护边界，继续细分会增加维护成本。

## 3. 版本与指纹

### 结论

不新增用户可维护的 `catalog_version`、基础数据版本或规则版本。快照仍是唯一历史追溯对象。

为保持既有快照和资源接口的 `base_data_version` 字段兼容，该字段继续存在，但语义收敛为“拆分配置集的只读内容指纹”：按相对路径和文件字节做确定性 SHA-256。它不展示为需要用户维护的版本，也不用于选择配置分支。

### 理由

- 历史快照必须能说明“当时用了什么配置”；完整快照已经满足该目标。
- 内容指纹只用于诊断和日志，不应成为用户需要理解的配置生命周期。
- 删除既有字段会造成契约破坏；保留字段但不引入新的版本语义是最小兼容方案。

## 4. 离线资源 CSV 导入

### 结论

资源 CSV 仍然只能通过离线命令导入。生成器只写：

- `deploy/data/kpi/base/metrics.json`
- `deploy/data/kpi/base/units.json`

永远不写规则目录下的任何文件。导入语义是完整替换基础指标和预留单位；CSV 中不存在的旧指标会被移除。移除后如果规则仍引用该指标，目录聚合校验必须失败，形成引用保护。

### 理由

- 资源 CSV 是全部基础资源的权威快照，避免旧指标无限残留。
- 规则文件不被生成器重写，避免离线导入覆盖人工维护的公式、阈值、容量和展示规则。
- 引用保护发生在生成或加载目录时，不需要数据库参与。

## 5. 一次性迁移

### 结论

在本功能的实现变更中直接提交迁移后的拆分文件，并删除 `deploy/data/kpi_catalog.json`。运行时不做自动迁移，也不提供旧文件回退。

### 理由

- 当前仓库内的配置就是唯一待迁移现场，一次性 Git 变更最简单、可审查。
- 运行时自动迁移会引入“到底读旧文件还是新文件”的边界复杂度，并违反“迁移后旧文件不再是权威来源”的要求。
- 已完成任务快照无需迁移；其内容表示历史配置，保持只读。

## 6. 任务快照边界

### 结论

快照路径和契约保持不变：

```text
output/<task_id>/kpi/kpi_catalog_snapshot.json
```

- 新任务在首次需要 KPI 配置时生成快照。
- 任何已有有效快照都不得被配置变化或重跑覆盖。
- 指定规则重跑发现已有任务缺少快照时必须失败，不能使用当前配置重建历史快照。
- 全量重跑沿用既有执行入口：不覆盖既有快照；快照缺失时允许按新任务初始化语义补写一次，指定规则重跑则不允许补写。

### 理由

- 完整快照是历史结果可解释的最低成本方案。
- 缺失快照的旧任务无法可靠恢复“当时配置”，使用当前配置会造成误导。
- 区分“新任务初始化”和“历史补写”可以避免把当前配置伪装成历史配置。

## 7. 校验策略

目录聚合时执行统一校验：

1. 每个 JSON 的必填字段、未知字段、类型和取值范围。
2. 基础指标与预留单位的全局唯一性。
3. 指标规则、阈值、容量规则和展示规则的引用存在性。
4. 公式派生依赖无循环。
5. `ME_*` 指标 `unit_key` 当前必须为 `null`；单位只登记，不参与计算。
6. 文件缺失、解析失败或校验失败时返回带相对路径和上下文位置的错误，不回退旧配置。

现有单文件校验器已经覆盖大部分规则语义；实现时拆分读取层，并保留或下沉这些校验函数。
