# 功能规格：KPI 基础数据入库与分类状态存储

**功能分支**：`feature/kpi-git-db-catalog`

**创建日期**：2026-09-18

**状态**：草稿

**输入**：用户描述：“基础数据提交到 Git 上，分类好的指标数据存入数据库；不需要离线的那几个 YAML。”

## Clarifications

### Session 2026-09-18

- Q: 移除旧的 KPI YAML 后，公式、阈值和容量规则应该在哪里维护？ → A: Git 规则数据——公式、阈值、容量规则随基础数据版本化，数据库只保存分类状态。
- Q: 原始资源 CSV 是否直接提交到 Git？ → A: 不直接提交。原始 CSV 只作为工具输入，工具解析校验后生成确定性、可版本化的 KPI 基础数据文件，并把该生成物提交到 Git。
- Q: 生成工具保留哪些能力？ → A: 只提取 CSV 中的原始指标数据并按稳定 key 排序；不推断基础指标类型、聚合方式、公式、阈值或展示规则。

### Session 2026-09-19

- Q: 公式、阈值、容量语义和展示规则采用哪种版本化文件组织？ → A: 单一 JSON 文件。
- Q: KPI 业务域分类是否支持自定义？ → A: 首版不支持自定义业务域或新增域，仅支持在 call/api/media 之间分类；自定义标签留作后续能力。
- Q: 旧 KPI 配置的一次性迁移范围是什么？ → A: 只迁移分类状态；公式、阈值、容量语义和展示规则由维护者整理到 Git JSON 规则文件，迁移工具只校验分类、冲突和引用完整性。
- Q: 现有在线上传资源 CSV 导入接口如何处理？ → A: 移除；基础指标变化只能通过离线工具生成并提交 Git，在线保留资源查询和分类能力。
- Q: 是否移除现有 KPI CSV 草稿生成模式？ → A: 移除；生成工具只保留资源 CSV 到排序基础指标数据的转换。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 维护版本化的 KPI 基础全集（优先级：P1）

配置维护人员把资源系统导出的 KPI 基础全集 CSV 放入本地输入目录，用工具解析并生成项目内的版本化原始基础数据。资源 ID、中英文名和单位随项目版本一起评审、变更和回滚。系统始终从生成后的权威基础数据加载指标基础信息，而不是让在线分类过程生成或改写基础定义；原始 CSV 不是运行时依赖。生成工具不推断业务语义和执行规则。

**优先级理由**：基础全集是分类、巡检和展示的共同来源；先固定权威来源，才能保证分类结果可信。

**独立测试**：修改或回滚基础数据版本后，重新打开 KPI 资源页面，能看到基础指标随版本变化，且分类状态不会被基础数据文件意外改写。

**验收场景**：

1. **给定**仓库中已提交由合法资源 CSV 生成的 KPI 基础数据，**当**用户打开 KPI 资源页面，**则**页面展示该版本中的全部有效指标基础信息。
2. **给定**基础数据新增、修改或移除了指标，**当**系统重新加载基础数据，**则**有效指标列表与该版本一致，且历史任务快照保持不变。

---

### 用户故事 2 - 在线分类结果持久化到数据库（优先级：P1）

运营人员在 KPI 资源页面搜索未分类指标，并把一个或多个指标归入 `call`、`api` 或 `media`。系统把分类状态、操作人和审计信息保存到数据库；在线分类不再写领域配置文件，也不再要求用户提交或同步 YAML 变更。

**优先级理由**：分类是运营过程中的可变业务状态，数据库可以提供事务、并发控制和审计能力。

**独立测试**：在不修改项目基础数据的情况下完成分类、重启服务并刷新页面，分类状态仍然保持。

**验收场景**：

1. **给定**三个未分类指标，**当**用户批量选择并分类到 `media`，**则**三个指标在同一事务语义下全部变为 `media`，失败时不出现部分保存。
2. **给定**指标已分类为 `api`，**当**另一个用户在过期页面上提交改为 `call`，**则**系统返回冲突，不静默覆盖最新状态。
3. **给定**分类保存成功，**当**用户查看审计记录，**则**能看到操作时间、操作类型、目标指标、来源状态和目标状态。

---

### 用户故事 3 - 运行时组合基础数据与分类状态（优先级：P1）

巡检执行人员运行任务时，系统把版本化基础数据和数据库中的有效分类状态组合成运行时 KPI 目录。执行器只使用组合后的有效目录，不再读取为分类结果而维护的离线领域文件。

**优先级理由**：这是新存储模型的核心价值；只有运行时真正使用组合结果，才能消除 YAML 双写和同步问题。

**独立测试**：使用相同基础数据版本和相同分类状态运行任务，得到相同的 KPI 指标目录；修改分类状态后再次运行，新任务使用新目录，旧任务结果不变。

**验收场景**：

1. **给定**某指标在数据库中属于 `api`，**当**执行 KPI 巡检，**则**该指标按 `api` 域规则参与匹配、聚合和展示。
2. **给定**基础数据中存在某指标但数据库没有分类记录，**当**执行 KPI 巡检，**则**该指标保持未分类，不进入任一业务域。
3. **给定**运行时环境不包含旧的领域配置文件，**当**启动 KPI 巡检，**则**系统仍能基于基础数据和分类状态构建有效目录。

---

### 用户故事 4 - 平滑迁移并退役旧 YAML（优先级：P2）

系统管理员执行一次性迁移后，现有领域文件中的指标分类关系进入数据库；公式、阈值、容量语义和展示规则由维护者整理到 Git JSON 规则文件，迁移工具不迁移规则数据。迁移报告标出成功、重复、冲突和无法迁移项。迁移完成后，旧的资源库文件和领域文件退出运行时依赖，不再作为新增或修改目标。

**优先级理由**：已有环境和历史配置必须能升级，不能因存储方式变化丢失分类和规则。

**独立测试**：迁移前后对比每个指标的归属、阈值、公式和容量语义，确认没有丢失或重复。

**验收场景**：

1. **给定**旧环境存在已分类指标，**当**执行迁移，**则**数据库中的分类状态与旧配置一致。
2. **给定**旧配置中存在引用保护或配置校验失败，**当**执行迁移，**则**系统给出明确错误，不产生部分迁移结果。
3. **给定**迁移完成，**当**用户再次执行导入、分类或巡检，**则**系统不再创建或更新旧的领域配置文件。

---

### 用户故事 5 - 保证历史任务可追溯（优先级：P2）

审计人员查看历史 KPI 任务时，能看到该任务使用的基础数据版本、分类版本和有效指标快照。即使之后基础数据或分类状态变化，历史任务的指标定义和归属解释仍可还原。

**优先级理由**：巡检结果必须可追溯；配置可变后，单靠当前文件或当前数据库状态不足以解释历史结果。

**独立测试**：完成任务后修改分类，再打开历史任务详情，历史任务展示的指标定义、域归属和规则版本保持原样。

**验收场景**：

1. **给定**任务已完成，**当**基础数据或分类状态随后变化，**则**历史任务详情继续展示执行时的指标快照。
2. **给定**任务结果包含 KPI 规则版本信息，**当**审计人员查看结果，**则**能识别基础数据版本和分类状态版本。

---

### 边界情况

- 当资源 CSV 出现重复资源 ID、重复稳定 key、非法 ID 或非法表头时，生成工具必须失败并给出文件、行号或资源 ID 定位信息，不能生成部分基础数据。
- 当基础数据中出现重复资源 ID、重复稳定 key 或非法 ID 时，系统必须加载失败并给出文件、行号或资源 ID 定位信息，不能把部分数据暴露为有效目录。
- 当基础数据移除了已有分类记录对应的指标时，系统不能让该分类继续生成有效领域指标；记录应保留并可识别为失效，便于基础数据恢复后继续使用。
- 当在线分类请求并发提交时，系统必须保证一个指标最终只有一个有效业务域，过期请求必须收到冲突提示。
- 当批量分类中部分指标被其他配置引用且不允许换域时，系统必须整体拒绝或明确排除；不得静默产生部分结果。
- 当数据库不可用或校验失败时，系统不能静默回退到旧 YAML 或空目录。
- 当基础数据引用的公式输入缺失时，有效目录校验必须失败并提示缺失项。
- 当旧配置迁移时出现重复定义或冲突，系统必须阻止迁移完成并保留原环境不变。

## 需求 *(必填)*

### 功能需求

- **FR-001**：系统必须支持把 KPI 基础全集作为项目内版本化基础数据维护，并以此作为指标基础定义的唯一事实来源。
- **FR-022**：系统必须提供离线工具读取资源全集 CSV，校验后生成项目内版本化 KPI 基础数据文件；原始 CSV 不作为运行时事实来源，也不要求提交到 Git。
- **FR-023**：工具只提取原始指标数据，生成的基础数据必须包含资源 ID、稳定 key、中文名、英文名和单位；不得包含业务域分类状态、生成时间、推断类型、聚合方式、公式、阈值或展示规则。
- **FR-024**：相同资源 CSV 输入必须生成字节一致的基础数据文件；指标必须按稳定 key 排序，并记录资源输入内容摘要用于溯源。
- **FR-025**：`UNIT_` 单位记录必须被工具过滤，不进入基础指标列表；中文描述末尾括号中的单位应拆分为独立单位字段。
- **FR-002**：系统必须从版本化基础数据加载资源 ID、稳定 key、中文名、英文名和单位；不得由在线分类过程改写这些基础字段。
- **FR-003**：系统必须继续使用小写资源 ID 作为稳定 key，不得引入别名机制。
- **FR-004**：系统必须继续将 `ME_` 前缀识别为指标资源，`UNIT_` 前缀识别为单位资源；单位资源不进入 KPI 指标列表。
- **FR-005**：系统必须校验基础数据的表头、资源 ID、稳定 key、必填名称和引用关系；校验失败时不得生成部分有效目录。
- **FR-006**：系统必须把业务域分类作为数据库中的可变状态持久化。
- **FR-007**：系统必须保证一个指标在同一时间最多有一个有效业务域；没有分类记录时展示为未分类。
- **FR-008**：用户必须能够通过 KPI 资源页面执行单条和批量分类，目标域仍限于 `call`、`api` 和 `media`；首版不支持自定义业务域、新增业务域或自定义标签。
- **FR-009**：系统必须原子保存单条或批量分类；任一保存失败时，本次变更不得部分生效。
- **FR-010**：系统必须为导入校验、分类和迁移保留审计信息，至少包括操作时间、操作类型、目标指标、操作前状态、操作后状态和结果。
- **FR-011**：系统必须在运行时组合版本化基础数据和数据库分类状态，形成有效 KPI 指标目录。
- **FR-012**：系统必须在组合有效目录时保证 key 唯一、引用完整、域归属唯一。
- **FR-013**：运行时和在线分类流程不得读取、生成或更新用于保存资源库与领域分类结果的离线配置文件。
- **FR-014**：系统必须保留现有 KPI 巡检能力；公式、阈值、容量语义和展示规则在移除旧文件前必须有等价的版本化数据来源。
- **FR-021**：公式、阈值、容量语义和展示规则必须作为版本化基础规则数据维护，并支持随项目版本评审和回滚；这些规则统一保存在单一 Git JSON 文件中，数据库不得作为这些规则的事实来源。
- **FR-015**：系统必须在任务结果或任务元数据中记录本次使用的基础数据版本、分类状态版本和有效指标快照。
- **FR-016**：系统必须提供从旧配置到数据库分类状态的一次性迁移能力，只迁移分类状态并输出迁移摘要；公式、阈值、容量语义和展示规则不得写入数据库。
- **FR-017**：迁移必须可校验；存在丢失、重复、冲突或引用不完整时，系统必须保持原状态并阻止标记迁移完成。
- **FR-018**：系统必须继续防止已公式、阈值或容量配置引用的指标被重新分类；迁移和在线分类都必须执行引用保护。
- **FR-019**：本地模式和在线模式使用相同的有效目录组合规则；同一基础数据版本和分类状态必须产生同一巡检输入。
- **FR-020**：涉及 KPI 资源查询、分类、迁移或任务结果的接口变更必须先更新接口契约，再同步实现、前端调用和测试。
- **FR-026**：系统不得提供在线上传资源 CSV 并导入基础指标的接口；资源 CSV 只能通过离线工具读取并生成 Git 版本化基础数据文件。
- **FR-027**：生成工具必须只支持资源 CSV 到基础指标数据的转换，并按稳定 key 排序；不得扫描 KPI CSV、生成领域草稿、推断类型或聚合、推导公式或维护别名。

### 关键实体 *(如果功能涉及数据则填写)*

- **KPI 基础指标**：随项目版本维护的原始指标全集记录，包含资源 ID、稳定 key、中文名、英文名和单位；不包含在线分类状态，也不包含工具推断的类型、聚合、公式、阈值或展示规则。
- **KPI 基础数据生成源**：资源系统导出的离线 CSV 快照，包含 `ME_` 指标和 `UNIT_` 单位记录；仅作为生成工具输入，不进入运行时目录。
- **分类状态**：一个基础指标当前是否属于 `call`、`api`、`media` 或保持未分类的运营状态；同一指标最多一个有效归属。
- **分类审计**：一次分类或迁移操作的证据，包含操作者、时间、变更前后状态和结果。
- **有效 KPI 指标目录**：基础数据与分类状态组合后的运行时结果；只包含基础数据中存在且分类有效的指标。
- **KPI 规则定义**：与指标相关的公式、阈值、容量语义和展示规则；必须随基础能力一起可校验和可追溯。
- **任务配置快照**：任务执行时的基础数据版本、分类版本和有效指标定义，用于解释历史结果。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**：加载 1000 行以内的基础全集后，用户能在 2 分钟内看到全部有效指标，并可按资源 ID 或中英文名检索。
- **SC-002**：一次批量分类最多 100 个指标时，全部成功保存的耗时不超过 1 分钟；失败时不产生部分有效归属。
- **SC-003**：重复加载相同版本基础数据后，有效指标数量、key 和基础字段完全一致。
- **SC-007**：相同资源 CSV 重复执行生成工具时，基础数据文件内容保持字节一致；分类状态不受重新生成影响。
- **SC-004**：旧配置迁移后，指标分类归属的迁移一致率达到 100%；无法迁移项必须全部出现在迁移报告中。公式、阈值和容量语义不进入数据库，由维护者迁移到 Git JSON 后通过规则校验确认。
- **SC-005**：在移除旧领域配置文件的运行环境中，KPI 巡检仍能完成构建目录、执行规则和输出结果。
- **SC-006**：基础数据或分类状态变化后，已完成任务的指标快照、域归属和规则版本保持 100% 不变。

## 假设

- KPI 基础全集仍然是离线资源快照；本功能不引入对被检系统的在线采集。
- 分类状态使用本地默认数据库即可满足当前部署，不需要强制引入外部数据库服务。
- `call`、`api`、`media` 仍是首版业务域；新增业务域属于后续扩展。
- 公式、阈值、容量语义和展示规则不是“在线分类状态”本身；本功能必须保留其能力，但具体在线编辑方式可以在后续功能中设计。
- 旧领域配置只作为迁移来源；迁移完成后不再作为运行时事实来源。
- 桌面浏览器仍是主要操作入口，不要求移动端适配。
