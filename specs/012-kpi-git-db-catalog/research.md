# 研究结论：KPI 基础数据入库与分类状态存储

## 1. 权威数据放置

**决策**：单一权威文件使用 `deploy/data/kpi_catalog.json`。

**理由**：

- 该文件是随项目版本评审的基础与规则数据，不是在线写入的运行配置。
- 与 `deploy/config/` 中面向程序的历史 YAML 分离，避免误把它当作可在线更新的配置。
- 单文件满足规格澄清：指标、单位预留、公式、阈值、容量语义和展示规则一起版本化。
- 文件不写入 `base_data_version` 字段；基础数据版本由整个 JSON 文件字节内容的 SHA-256 计算，避免自引用。

**替代方案**：

- 继续使用多个 YAML：不符合单一 JSON 结论，且无法表达统一的引用校验与快照边界。
- 数据库存基础定义：违反“Git 保存权威基础定义，数据库只保存分类状态”。
- 在 JSON 内写入内容版本：会造成自引用或需要元数据文件，复杂且不必要。

## 2. 离线生成工具边界

**决策**：提供只读资源 CSV、更新单一 JSON 中 `metrics` / `units` / `source_csv_sha256` 的离线命令。工具不迁移 YAML，不扫描 KPI 数据 CSV，不推断类型、聚合、公式、阈值或展示规则。

**命令形态**：

```bash
.venv/bin/python -m app.tools.kpi_catalog generate \
  --csv <resource_snapshot.csv> \
  --output deploy/data/kpi_catalog.json
```

**行为**：

- 仅接受资源全集 CSV，表头固定为 `资源id,中文描述,英文描述`。
- `ME_*` 记录进入 `metrics`，`UNIT_*` 记录进入 `units`。
- 指标与单位都按稳定 key 升序排序；`metrics[].unit_key` 固定为 `null`。
- `source_csv_sha256` 记录原始 CSV 字节内容摘要。
- 已存在输出文件中的 `rules` 只被读取和保留，不被生成器改写。
- 生成前按新基础指标校验规则引用；引用缺失时失败，不输出部分文件。
- 输出使用 UTF-8、LF、稳定缩进和稳定键序；相同 CSV 与相同规则输入必须字节一致。

**替代方案**：

- 在线导入 CSV：违反离线维护边界，已由规格明确移除。
- 生成器同时迁移 YAML：会把当前非权威样例指标带入新模型，已明确禁止。
- 记录导入时间：破坏确定性，无法满足相同 CSV 字节一致。

## 3. 运行时组合模型

**决策**：运行时使用三层数据。

1. Git JSON 提供基础指标、单位预留、规则定义。
2. 数据库提供每个基础指标当前的业务域分类状态。
3. 任务启动时组合成有效目录并写入任务快照。

**组合规则**：

- 基础数据校验失败时目录加载失败。
- 分类记录指向的基础指标不存在时保留为失效记录，但不进入有效目录。
- 只有基础数据存在且分类为 `call` / `api` / `media` 的指标进入对应领域有效指标列表。
- 数据库没有分类记录时保持 `unclassified`。
- 公式输入必须存在于基础指标；输入可以是未分类，但派生结果所属指标必须已分类才能进入领域执行。
- 公式、阈值或容量规则引用的指标在已分类状态下不能换域或改回未分类；从未分类到首次分类允许，用于完成初始配置。

**替代方案**：

- 每条规则直接读数据库：会造成任务内配置变化，破坏历史可追溯。
- 分类状态写入任务快照后作为后续重跑事实来源：违反“本地读取同一套数据库，不回退任务快照”。
- 使用旧 YAML 回退：明确禁止。

## 4. 数据库与并发

**决策**：使用现有默认 SQLite 与 SQLAlchemy 模型，不引入外部数据库作为默认依赖。

**数据表**：

- `kpi_classifications`：当前分类状态，一个 `metric_key` 一行。
- `kpi_classification_revisions`：单一递增修订行。
- `kpi_classification_audits`：分类操作审计。

**事务规则**：

- 单条和批量分类必须在同一数据库事务中完成。
- 任一指标校验失败时整批回滚。
- 成功批量请求只递增一次 `classification_version`。
- 不做乐观并发校验，不接收期望修订号；成功请求按提交和完成顺序生效。
- 数据库连接失败、事务失败或基础文件校验失败时返回错误，不回退 YAML 或空目录。

**替代方案**：

- JSON 文件存分类：无法满足数据库可变状态与审计要求。
- 每个指标递增修订号：会让任务快照版本语义碎片化。
- 乐观锁：规格明确判定分类是低频治理操作，不做乐观并发。

## 5. 历史可追溯

**决策**：任务启动时生成 `output/<task_id>/kpi/kpi_catalog_snapshot.json`。

**快照内容**：

- `base_data_version`：Git JSON 文件 SHA-256。
- `classification_version`：读取分类状态时的数据库递增修订号。
- `captured_at`：UTC 时间。
- `metrics`：完整有效指标定义与归属。
- `rules`：完整规则定义，不裁剪到仅当前任务领域。

**读取规则**：

- 正常任务启动时读取 Git + 数据库并写入快照。
- 单规则重跑优先读取既有任务快照，保证历史任务不因后续配置变化改变语义。
- 快照缺失时才加载当前配置并补写快照。
- 快照校验失败时该任务继续执行失败，不回退当前 Git 或数据库状态。
- KPI 规则结果的 metadata 记录两个版本，任务快照 API 提供完整内容。

**替代方案**：

- 只记录版本号：无法解释当时的指标定义和规则内容。
- 每条 KPI 规则重复保存完整快照：数据重复且一致性维护成本高。
- 快照只保存分类：无法满足历史结果自解释。

## 6. API 演进

**决策**：为 KPI 资源与快照引入 `/api/v3`；不再提供 `/api/v2` 在线 CSV 导入。

**范围**：

- `/api/v3/kpi/resource-metrics`：分页查询基础指标和分类状态。
- `/api/v3/kpi/resource-metrics/classification`：单批原子分类，支持 `unclassified`。
- `/api/v3/tasks/{task_id}/kpi/catalog-snapshot`：查询任务配置快照。
- 其余既有 v2 接口暂不变更，避免把无关接口强行迁移。

**兼容性**：

- KPI 资源 API 的字段与分类请求属于不兼容变更，按项目红线进入新版本。
- 前端只调用生成的 `/api/v3` 资源客户端。
- 移除在线导入 UI 与生成的导入客户端方法。
- 旧 `/api/v2` 资源接口从契约和实现中删除；基础数据只能由离线工具进入 Git。

**替代方案**：

- 在 `/api/v2` 内修改请求字段并移除导入：违反破坏性变更必须进入新版本。
- 保留旧导入接口：违反规格。
- 全量迁移所有 v2 接口：扩大本次变更范围，且与 KPI 语义无关。

## 7. 单位预留

**决策**：解析并保留单位字典与 `unit_key` 字段，但不建立映射，不进入有效目录、数据库分类、任务快照有效指标、资源页面展示或运行时计算。

**理由**：满足“字段预留但不在本迭代设计和开发单位能力”的产品决策。规则定义中既有的展示 `unit` 字段属于当前巡检契约，不等同于建立 `ME_*` 到 `UNIT_*` 的映射。

**替代方案**：

- 完全不解析 `UNIT_*`：会丢失后续能力所需的权威预留数据。
- 按名称推断单位：明确禁止。
- 当前开放界面配置单位：明确延期。

## 8. 前端结构

**决策**：

- 页面和导航继续使用“KPI 指标库”。
- 移除资源 CSV 上传控件。
- 使用新版资源接口字段与分类请求。
- 分类成功后按返回修订号刷新；不传期望修订号。
- 为任务与 KPI 领域页面引入路由级懒加载，并把大型第三方库拆分到独立 chunk，消除构建告警。

**替代方案**：

- 保留旧上传按钮指向离线工具说明：会造成“在线可导入”的误解。
- 只调大 Vite 告警阈值：掩盖性能问题，不解决问题。
