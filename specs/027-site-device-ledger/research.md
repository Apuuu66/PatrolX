# 阶段 0 研究：局点设备台账

## 1. 台账存储位置

**Decision**：使用 SQLite 独立台账表持久化设备、观测、任务解析结果和审计；`inventory.json` 只作为任务级证据，不承担台账持久性。

**Rationale**：任务详情、报告和任务输出目录被定义为可重建资产，而设备台账是不可丢失资产。SQLite 已是默认部署基线，可以事务化保证“任务观测覆盖 + 审计记录 + 设备状态重算”的一致性。

**Alternatives considered**：

- 只写 `output/<task_id>/inventory.json`：任务输出清理或重建时存在资产丢失风险，且跨任务查询效率差。
- 建立独立局点表：规格确认局点只是 `province + operator` 组合，第一版不需要局点档案、负责人或拓扑。
- 使用 JSON 文件索引：并发覆盖和审计一致性弱于 SQLite 事务。

## 2. 台账解析是否作为 Inspector

**Decision**：台账解析放在 `app/services/inventory/` 共享服务，不注册为普通 Inspector，也不创建公共 prepare。

**Rationale**：台账不是规则结果，不应进入规则摘要、规则详情或报告规则列表；也不应声明 `source_patterns` 参与 `RuleResult` 契约。它需要在任务完成后影响跨任务持久状态，属于任务生命周期服务而不是单条巡检规则。

**Alternatives considered**：

- 实现 `inventory.lst_me` 规则：会误导用户把它当成普通巡检规则，并违反“prepare 不被其他规则消费”的规则隔离。
- 使用公共 prepare：会建立规则间共享数据通道，违反宪法。

## 3. 任务类型与 API 版本

**Decision**：新增 `POST /api/v3/tasks` 和 `PackageKind=inspection|log_supplement`；保留 `/api/v2/tasks` 不变；任务详情以可选字段增量携带 `package_kind` 和 `inventory`。

**Rationale**：v2 请求允许人工版本和设备 ID，并且局点可选。新的巡检包必须必填局点且版本只能来自包内文件，这是请求语义变化。放在 v3 可以避免改变既有 v2 字段含义。日志补充包必须由用户显式声明，不能从“缺少 `LST ME.txt`”推断。

**Alternatives considered**：

- 直接扩展 v2 并条件必填：会改变既有请求语义，属于破坏性变化。
- 只在前端隐藏版本：无法约束 CLI / API 客户端。
- 用文件名关键字识别日志包：不可靠，且会隐式决定任务是否进入台账。

## 4. `LST ME.txt` 分类与匹配

**Decision**：在分类配置中增加精确模式 `^LST ME\.txt$`，让该文件进入 `config` 工作现场。台账解析服务在 `config/` 下按相对路径正则匹配 `^config/(?:.*/)?LST ME\.txt$`。

**Rationale**：现有 `.txt` 不属于 config 扩展名，若不调整分类，文件可能进入 `other`。解析服务不应在整个任务目录中模糊搜索，应依赖安全解压后的分类现场和固定文件名。

**Alternatives considered**：

- 在上传前直接打开 zip 查找文件：绕过安全解压和分类现场，重复读取原始包。
- 按内容嗅探：文件名固定且足够可靠，内容嗅探会增加误判。
- 只匹配 `config/LST ME.txt` 平铺路径：无法覆盖保留原始目录层级的证据现场。

## 5. 字段解析与编码

**Decision**：使用统一文本解码入口，至少兼容 UTF-8 和 GB18030；按命令输出中的键值行解析设备名和版本；设备名和版本支持已确认的中英文别名。

**Rationale**：`LST ME.txt` 是命令输出样式的固定文件，不是 CSV 或结构化 JSON。键值行解析容错性好，同时能保留原始行号和来源证据。统一解码入口满足项目全局编码兼容约束。

**Aliases**：

- 设备名：`NE name`、`ME name`、`网元名称`、`设备名称`
- 版本：`Software version`、`SW version`、`软件版本`

**Parse rules**：

- 一个任务代表一台设备；多个不同设备名记为设备身份冲突，不归档观测。
- 多个不同版本在有效设备身份下仍归档观测，但版本状态为 `conflict`，当前版本不更新。
- 重复相同值不视为冲突。
- 缺少版本不阻断观测归档。
- 缺少文件、无法解析设备身份或编码失败时返回明确状态，不中断任务。

## 6. 设备身份

**Decision**：设备身份是 `province + 规范化设备名`。规范化顺序为 Unicode NFC、去首尾空白、连续空白合并为一个空格；不做大小写转换。运营商不参与设备身份。

**Rationale**：规格确认同省份设备名不重复，省份外的同名设备必须区分；同省份跨运营商同名设备是同一设备的局点归属变化。该规则避免把不同省份设备误合并。

**Storage**：`device_key` 使用规范化字段生成的确定性 SHA-256 摘要，业务展示仍使用规范化设备名；数据库同时以 `(province, device_key)` 唯一约束防止并发重复建档。

## 7. 版本方向

**Decision**：只按原始版本字符串的 Unicode 字典序判断相邻有效版本方向；当前版本取最近一次成功解析版本的观测值。

**Rationale**：规格明确不做版本号语义拆解。历史版本路径可能包含回退，最大字典序不代表当前运行版本。

**Effects**：

- `V1 → V2` 为 `upgrade`，`V2 → V1` 为 `downgrade`，相等为 `unchanged`。
- 版本缺失、冲突或解析失败保留时间线缺口，不参与方向计算。
- 不生成数字主版本、补丁层级或语义版本比较结果。

## 8. 幂等归档与审计

**Decision**：每个任务在 `inventory_observations.task_id` 上唯一；全量重跑或重建按任务覆盖当前生效观测。覆盖前保存 `before_snapshot`，覆盖后保存 `after_snapshot`；结果未变化时不重复写审计。若再次归档不再得到有效观测，将既有观测标记为 `retired` 并保留审计，不物理删除。

**Rationale**：包内容不可变且解析器确定时，通常不会变化；但解析器升级或分类策略变化可能导致结果变化。唯一约束可防止重复观测；审计可保证被替换的前一版台账资产可追溯。

**Alternatives considered**：

- 追加多条观测：违反“每个任务最多一条当前生效观测”。
- 直接删除旧观测：会破坏可追溯性，不符合台账资产保护要求。
- 全量删除设备后重建：会把跨任务资产绑定到单任务生命周期，风险高。

## 9. 任务生命周期接入

**Decision**：全量任务执行和全量重建完成后调用共享归档入口；增量重建和单规则重跑不改变台账。

**Rationale**：台账观测代表一次完整任务；单规则结果重跑不是新的设备观测，也不应导致版本时间线变化。任务完成后归档可以避免 pending / running 任务产生中间状态。

**Failure policy**：

- 台账解析或写库异常记录任务日志和结构化错误，不把任务置为失败。
- 任务没有正常完成时不归档。
- 日志补充包直接生成 `not_applicable` 证据，不进入解析器。

## 10. 查询分页与前端信息架构

**Decision**：设备列表、观测历史、版本历史和质量问题列表全部分页，默认 `page_size=10`。前端局点视图先选择省份和运营商，设备详情再展开历史局点。

**Rationale**：符合项目分页默认；也避免把多个局点的同名设备误显示在当前局点。设备当前局点跟随最近一次有效观测，历史局点只在设备详情时间线中追溯。

**UI source**：OpenDesign 用于视觉稿和交互验证；最终接口和数据口径以 Speckit 契约与 OpenAPI 为准。

## 11. 删除与历史回填

**Decision**：第一版不定义任务删除后台账保留策略，也不回填历史任务。

**Rationale**：规格明确两者范围外。实现不得因为顺手而引入删除级联或自动回填；后续应单独规格化，明确用户确认、审计和版本观测补齐规则。
