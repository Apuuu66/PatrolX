# 研究报告：任务详情统计数字过滤

## 决策 1：总览状态数量数据来源

**决策**：总览状态数量由详情页已加载的可见规则列表在前端推导，不依赖后端 `task.stats` 字段。

**理由**：详情页已经加载了完整的 `SystemInspection.rules` 列表（已过滤隐藏规则），从中按状态统计即可保证总览数字与实际展示列表始终一致。后端 `task.stats` 可能包含隐藏的内部解压规则，直接使用会导致点击过滤后列表条数与总览数字不一致。

**备选方案**：
- 使用后端 `task.stats` 字段：被否决，因为可能包含隐藏规则且需要修改后端口径。
- 新增后端接口返回过滤后统计：被否决，因为增加了不必要的网络请求和契约变更。

## 决策 2：过滤状态管理方式

**决策**：在 `TaskDetailPage` 中使用 React 内部状态管理过滤条件，不引入 URL 参数持久化或全局状态管理。

**理由**：过滤是页面内临时排查视角，生命周期与当前页面会话一致。同一时间最多只有一个激活状态，使用简单的单值状态即可满足需求。

**备选方案**：
- URL 查询参数持久化：被否决，因为过滤是临时操作，用户不需要通过 URL 分享过滤结果。
- Redux/Zustand 等全局状态管理：被否决，因为过滤只在任务详情页内使用，全局状态增加不必要的复杂度。

## 决策 3：交互方式

**决策**：总览状态数量卡片可点击；点击未激活状态时设置过滤，点击已激活状态时取消过滤。使用视觉反馈（如边框/阴影变化）标识当前激活的过滤状态。

**理由**：与现有 Ant Design 卡片风格一致，交互简洁；单次点击完成设置和取消，无需额外的"清除筛选"按钮。

**备选方案**：
- 独立"清除筛选"按钮：被否决，因为再次点击同一状态即可取消，增加冗余交互。
- 下拉框选择状态：被否决，因为总览数字本身就是状态入口，下拉框增加中间步骤。

## 决策 4：组件变更边界

**决策**：`SummaryCards` 组件新增可选的点击回调属性和激活状态属性；`TaskDetailPage` 负责管理过滤状态并将过滤后的规则列表传递给分类分组卡片。

**理由**：保持 `SummaryCards` 作为纯展示组件，通过回调与父组件通信；过滤逻辑集中在 `TaskDetailPage`，避免组件间状态同步问题。

**备选方案**：
- `SummaryCards` 内部管理过滤状态并直接操作列表：被否决，因为 `SummaryCards` 与规则列表不在同一层级，需要通过全局状态或事件总线通信，增加耦合。

## 决策 5：测试策略

**决策**：使用 Vitest 编写前端单元测试，覆盖过滤设置、取消、替换、数据刷新保留和空状态场景。

**理由**：过滤逻辑是纯函数级别的状态变更，适合单元测试验证；无需端到端测试即可覆盖核心行为。

**备选方案**：
- Playwright/Cypress 端到端测试：被否决，因为本项目当前未配置端到端测试基础设施，且核心行为可通过单元测试验证。
