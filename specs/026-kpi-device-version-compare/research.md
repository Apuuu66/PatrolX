# 研究结论：KPI 同设备版本对比

## 结论

1. **版本来源**：使用 `task.json` / `TaskSummary.customer_version`，不是 `rule_version`。缺失时显示“版本未知”。
2. **设备来源**：使用 `system.customer.device_id`；缺失时直接降级，不猜测归属。
3. **基线任务选择**：同设备、同版本、已完成、有完成时间；同一版本选择完成时间最新任务，界面显示任务 ID 和完成时间。
4. **点位来源**：继续使用任务私有 `kpi/history/index.jsonl`；按行 JSON 解析，坏行跳过。
5. **对比维度**：`measurement_unit_id`、`metric_resource_id`、`object_key`、`period_minutes` 全部一致才输出基线点。
6. **摘要口径**：第一版当前值与基线值均使用平均值；输出绝对差值和比例。比例分母为基线均值绝对值，为 0 时比例为 null。
7. **曲线时间轴**：两个任务合并时间标签（`HH:mm`）后各画一条独立序列；不把多任务合并为一条混合曲线。
8. **窗口策略**：本功能不使用 7 天窗口。只要同设备、不同版本且任务点位有效即可显式对比；界面必须显示任务来源。
9. **API 形态**：新增 version-candidates 和 version-compare 两个接口，避免复用历史趋势模型造成字段语义混杂。
10. **性能**：候选读取元数据；对比逐行读取索引并尽早过滤维度，不加载规则结果 JSON 或整任务指标。

## 被放弃方案

- **扩展 history-trend 接口**：字段语义会和“多历史任务基线”混淆，前端状态也更复杂。
- **前端直接读取任务列表再筛选**：会把领域匹配逻辑放入前端，且无法保证候选口径统一。
- **自动重建旧任务**：违反本 spec 的只读历史约束。
