# 研究结论：界面规则启停

## 结论

本功能不新建独立服务形态，而是在现有离线巡检系统中补齐“规则启停状态管理、任务规则过滤和规则管理界面”三层能力。启停状态必须是可持久化的一等状态；既有 `deploy/config/scan_rules.yaml` 中的 `disabled_rules` 只承担首次初始化。

## 现状

- 规则由注册表装载；`InspectorInfo` 目前只返回规则定义，不包含启停状态。
- 现有 `disabled_rules` 在注册表装载时直接移除规则，导致禁用规则无法在界面回显，也不利于后续重新启用。
- 任务执行使用 `Executor` 生成解压、prepare 和普通巡检计划；目前普通规则计划只按注册表中的可见规则生成。
- 单规则重跑和增量重建都依赖规则代码选择目标规则；当前缺少停用状态校验。
- 前端已有规则列表页，适合扩展启停开关；前端 API 客户端由 OpenAPI 生成。
- 系统已有 SQLite 元数据库和登录角色体系；规则启停这类维护操作适合限制为管理员。

## 技术决策

1. **持久化状态**
   - 新增规则启停状态存储，字段至少包括规则代码、启用状态和最近变更时间。
   - 不保存完整审计历史。
   - 状态初始化时只对尚未有状态的普通规则使用 `disabled_rules`；已有状态不回写、不覆盖。

2. **注册表职责**
   - 注册表继续负责装载全部规则定义；禁用不再等价于从注册表删除。
   - 可管理范围由 `hidden` 判断：隐藏的内部前置规则不可启停。
   - 规则是否执行由启停服务提供的状态和执行器过滤共同决定。

3. **执行语义**
   - 新任务开始时读取一次启停状态，形成本次任务的规则集合。
   - 停用普通规则时，其私有 prepare 也不执行。
   - 隐藏解压规则始终执行；解压失败仍按现有契约任务失败。
   - 单规则重跑、增量重建选择停用规则时必须显式失败。
   - 全量重建按当前启停状态重新执行。

4. **接口契约**
   - 在现有 `/api/v2/inspectors` 返回结构中补充启停字段。
   - 新增启停更新接口，路径保持在 `/api/v2`。
   - 列表继续公开查看，更新操作要求管理员角色。
   - 支持按状态、分类和关键字筛选；前端可以先在列表内过滤。

5. **前端交互**
   - 复用现有规则列表页，不再新建独立页面。
   - 启用状态使用开关展示，停用规则使用可识别的视觉标记。
   - 普通维护人员可以查看状态，但无权切换；界面应禁用操作并依赖后端再次校验。
   - 切换成功后刷新当前列表；失败时展示后端返回的明确原因。

## 风险与约束

- 直接继续删除禁用规则会让“界面重新启用”不可实现，因此必须改为状态过滤。
- 必须防止 prepare 在 owner 停用后继续写任务现场。
- 必须防止旧任务结果在启停变化后被重算或删除。
- 需要同步 OpenAPI、Pydantic Schema、测试和前端生成客户端。
