# 功能规格：按真实目录进行按需归档分类

**功能分支**：`feature/038-on-demand-archive-classification`

**创建日期**：2026-11-02

**状态**：已澄清

**输入**：用户要求根据真实巡检包目录和文件重新规划分类，不只按文件名或扩展名猜测；只对明确需要分析的压缩包展开，只对明确需要读取的 GZIP 解压；UMF 做精细化分类，CSP 本阶段只保留告警；告警压缩包也必须展开并统一放入 `alarm/`；Service Logs 只保留业务主日志；分类结果必须可审计，并在配置变化后可靠重建。

## 用户场景与测试 *(必填)*

### 用户故事 1 - UMF 文件按真实来源目录精细落位（优先级：P1）

巡检人员上传 UMF 巡检包后，系统根据文件在场景目录中的真实来源路线选择业务分类和物理目标目录，不再依据文件名关键字、扩展名或压缩包内容嗅探猜测类别。不同来源目录允许对应同一业务分类；同一业务分类也可以按证据用途拆分为多个物理目录。

**优先级理由**：这是本次分类调整的核心。只有基于真实目录路线，才能避免同一 `.csv` 被统一误归 KPI、同名文件被错误合并，以及中间包装目录污染规则匹配路径。

**独立测试**：使用具有不同外层包装深度、但包含相同 UMF 场景目录的合成包执行分类，逐项核对基础配置、设备状态、调试命令、操作日志、MML、性能、MESH 指标和其他未命中文件的业务分类与目标路径；再增加一个未命中文件，验证其按场景相对路径进入 `other/`。

**验收场景**：

1. **给定** 文件位于 `Basic Information About the UMF/` 下，**当** 执行分类，**则** 文件进入 `basic/`，业务分类为 `config`，且不保留外层设备名和包装目录。
2. **给定** `Debugging Commands/`、`Equipment Status/`、`MESH Information (Problem)/` 和 `System Resources/` 下的文件，**当** 执行分类，**则** 分别按本规格映射进入 `debug/` 或 `status/`，业务分类均为 `status`。
3. **给定** `Performance Measurement Results/PerfResult_*.zip`，**当** 执行分类，**则** 归档内全部成员展开到 `kpi/`，不得根据成员是否为 `.csv` 或其他扩展名重新分类。
4. **给定** `MESH Application Metrics/CollectExport*.zip`，**当** 执行分类，**则** 归档内 CSV 展开到 `other/MESH Application Metrics/<归档名>/`，不得进入 `kpi/`。
5. **给定** UMF 场景中存在未命中任何明确路线的普通文件，**当** 执行分类，**则** 文件进入 `other/<场景相对路径>`，不得静默丢弃。
6. **给定** 两个不同来源目录产生相同目标路径，**当** 执行分类，**则** 不允许后写入项覆盖先写入项；两者都必须可从分类审计记录追溯，并通过稳定规则消除路径冲突。

### 用户故事 2 - UMF 和 CSP 告警统一展开并集中保存（优先级：P1）

巡检人员上传包含 UMF、CSP 或二者告警内容的巡检包后，系统识别所有真实告警目录中的告警文件，并将告警目录内的普通文件和压缩包成员统一放入同一个 `alarm/`。告警识别不依赖 `Problems` 等前置目录，也不因上传网元类型而漏掉另一类告警。

**优先级理由**：告警是当前明确关注的业务证据。真实 CSP 告警位于 `0/` 目录下，若沿用“跳过 0”的普通内容策略会直接漏掉告警；若继续使用全路径包含 `alarm/告警` 的宽泛匹配，又会误收非告警文件。

**独立测试**：分别构造 UMF `Alarm Information/**`、CSP `Alarm Data/**`、缺少 `Problems` 的 CSP 路径和位于 `0/` 下的告警，并加入 ZIP、TAR.GZ、单文件 GZIP、0 字节 CSV、仅表头和零记录 CSV；验证全部告警证据进入 `alarm/`，非告警 `0/` 内容仍被忽略，损坏归档只影响自身。

**验收场景**：

1. **给定** 路径任意前缀下存在完整目录段 `Alarm Information/`，**当** 执行分类，**则** 其后缀下的普通文件及递归归档成员全部进入 `alarm/`。
2. **给定** CSP 路径为 `.../0/Problems/Alarm Data/...`，**当** 执行分类，**则** 告警优先于 `0/` 忽略规则，文件进入 `alarm/`。
3. **给定** CSP 路径不再包含 `Problems`、但保留 `Alarm Data/`，**当** 执行分类，**则** 仍识别为告警。
4. **给定** 告警目录包含 ZIP、TAR/TAR.GZ 或单文件 GZIP，**当** 执行分类，**则** 递归展开或解压，并去掉告警来源目录层和归档外层，只保留归档内部真实相对路径。
5. **给定** UMF 与 CSP 各有告警，**当** 执行分类，**则** 所有告警文件位于同一 `alarm/`，业务分类均为 `alarm`，不按网元类型再分子目录。
6. **给定** `0/` 下存在告警以外的 CSP 文件，**当** 执行分类，**则** 不作为工作分类文件保留。

### 用户故事 3 - Service Logs 只保留业务主日志并解压（优先级：P1）

巡检人员上传 UMF 包后，系统只从 `Service Logs (Problem)/ServiceLogs_*.zip` 中保留当前关注的业务主日志，去掉归档外层并解压轮转 `.log.gz`；监控、启动、代理、检查脚本、运行数据库和报告类文件不进入日志工作现场。

**优先级理由**：真实归档含 403 个条目、316 个普通文件，但当前只需要 98 个业务主日志。全量保留和展开会制造大量无关日志，同时轮转日志未解压会导致业务日志无法直接读取。

**独立测试**：使用真实结构或等价合成归档执行分类，核对 UMFAcc、UmfService、CacheService、ResourceManageService 的业务主日志保留、路径结构、`.log.gz` 解压结果和排除项；并验证其他普通文件与归档不受影响。

**验收场景**：

1. **给定** 归档包含 `UMFAcc.log` 或 `UMFAcc_*.log.gz`，**当** 执行分类，**则** 保留并进入 `logs/UMFAcc/...`。
2. **给定** 归档包含 `UmfService.log` 或 `UmfService_*.log.gz`，**当** 执行分类，**则** 保留并进入 `logs/UmfService/...`。
3. **给定** 归档包含 `CacheService.log` 或 `ResourceManageService.log`，**当** 执行分类，**则** 保留并进入对应服务目录。
4. **给定** 选中文件以 `.log.gz` 结尾，**当** 执行分类，**则** 解压为同名 `.log`，并保持服务、节点、pod 和轮转层级。
5. **给定** 同一归档包含 `RScheck/`、`monitor_detect.log`、`UmfService_monitor.log`、`UFP_*.log`、`start/proxy` 日志、`bbox*.dat.txt`、`LocalLogReport.csv`、`dblog.tar.gz` 或 `UFP_MSS_2_0.zip`，**当** 执行分类，**则** 这些内容不进入日志工作现场，并在审计记录中标记为未选或忽略。
6. **给定** 真实基准包的 UMF Service Logs 归档，**当** 执行分类，**则** 恰好保留 98 个业务主日志，其中 85 个 `.log.gz` 解压后变为 `.log`，13 个原始 `.log` 直接保留。

### 用户故事 4 - 分类配置变化后从证据现场稳定重建（优先级：P2）

运维人员修改分类配置、上传网元类型或分类相关策略后，再次确保同一个任务解压完成时，系统识别分类快照变化，并从只读证据现场重建工作分类目录和审计结果，不复用旧分类现场。

**优先级理由**：分类目录和业务映射会随真实包结构调整。若配置变化仍复用旧现场，会出现目录看似已更新、实际结果仍来自旧规则的隐蔽错误。

**独立测试**：对同一数据包连续执行两次分类，第一次记录配置指纹和结果；仅修改空白或注释后再次执行应复用，修改任一有效分类规则或网元类型后再次执行应从证据现场重建，且证据文件和原始包校验和保持不变。

**验收场景**：

1. **给定** 分类配置仅在注释或格式空白上变化，**当** 再次确保解压，**则** 语义指纹不变并允许复用分类结果。
2. **给定** 任一来源路线、优先级、动作、保留模式或目标模板发生语义变化，**当** 再次确保解压，**则** 分类指纹变化并完整重建分类工作现场。
3. **给定** 上传网元类型从 UMF 变为 CSP，**当** 再次执行分类，**则** 使用对应网元规则集重新分类，不得复用旧网元规则结果。
4. **给定** 证据现场完整且校验和一致，**当** 重建分类现场，**则** 不再读取新的外部输入，也不修改原始上传包。
5. **给定** 证据现场缺失或损坏，**当** 重建分类现场，**则** 从原始上传包重新建立证据现场后再分类。
6. **给定** 分类配置无效，**当** 开始任务解压，**则** 任务以明确配置错误失败，不得使用空规则、部分规则或旧规则继续执行。

### 用户故事 5 - 分类过程可审计且巡检清单只含成功落位文件（优先级：P2）

运维人员查看分类日志时，能够确认每个来源文件采用了哪条路线、得到什么业务分类、被放到哪里、执行了什么动作、是否跳过或失败，以及本次使用的配置指纹。巡检规则只会看到分类清单中标记为成功落位的文件。

**优先级理由**：分类错误往往不是解析错误，而是文件在进入解析前被错误归类、忽略或覆盖。没有逐文件审计，无法定位“为什么某个巡检规则没有执行”。

**独立测试**：构造命中、未命中、忽略、冲突、损坏归档和解压超预算场景，检查分类摘要与逐文件审计字段；随后执行普通规则，确认其匹配范围只来自成功落位文件。

**验收场景**：

1. **给定** 文件成功分类，**当** 查看审计记录，**则** 能看到来源相对路径、命中路线、业务分类、目标相对路径、动作、状态和配置指纹。
2. **给定** 文件被规则明确忽略，**当** 查看审计记录，**则** 记录忽略原因，且不进入巡检文件清单。
3. **给定** 归档局部损坏或预算不足，**当** 分类结束，**则** 该项记录失败原因，其他合法文件继续落位且任务不因单文件失败中断。
4. **给定** 普通规则没有匹配任何成功落位文件，**当** 执行规则，**则** 返回 `skip` 和非空原因，不得静默通过。
5. **给定** 同名文件因不同来源到达同一目标，**当** 查看结果，**则** 不发生静默覆盖，冲突解决后的实际目标与来源均可追溯。

### 边界情况

- 主包外层设备目录、问题场景目录和包装层级数量可以变化；路线按归一化路径中的真实目录后缀匹配，不依赖固定绝对深度。
- `Problems` 可能缺失或改名，CSP 告警不能依赖该目录段；只依赖 `Alarm Data/` 及之后的后缀。
- 路径匹配大小写不敏感，但落位后的业务文件名和目录名保留来源中的原始大小写，除非目标结构明确要求固定目录。
- `0/` 对普通内容继续忽略；`Alarm Information/` 和 `Alarm Data/` 的告警路线优先级高于 `0/` 忽略。
- “0 告警”表示文件内容代表零条告警记录，不等于文件大小为零。告警路线中的 0 字节文件、仅表头文件、零记录文件和包含记录的 CSV 均先正常落位；是否为空或是否有效由后续解析区分。
- `.tar.gz` 先按归档展开，再处理成员中的单文件 GZIP；不得把 `.tar.gz` 误判为单文件 GZIP。
- 未明确声明展开的未知压缩包原样进入 `other/<场景相对路径>`，不得通过查看成员名称或内容自动展开。
- 压缩包损坏、路径穿越、链接、重复成员、目标过长、解压炸弹、深度或资源预算超限时，只允许影响对应条目并产生明确失败记录；主包本身无法建立证据现场时任务失败。
- 同一文件可能命中多个来源描述时，按配置声明优先级稳定选择首个路线；告警优先级和 `0/` 忽略优先级不得由配置顺序意外反转。
- 业务分类与物理目录为两个独立概念：多个来源目录可映射到 `status` 等同一业务分类，同一业务分类也可落位到 `debug/`、`status/` 等不同物理目录。
- 日志补充包没有网元类型，不参与 UMF/CSP 精细分类和台账匹配，继续使用通用日志补充分类流程。
- CSP 本阶段除告警外不做精细分类；其非告警内容不进入工作分类现场。
- 真实包目录整体的 `0/` 不代表“零条告警记录”，两者不得在日志或界面中使用同一含义。

## 需求 *(必填)*

### 功能需求

#### 输入、网元类型与规则选择

- **FR-001**：系统必须允许巡检包在创建时指定网元类型，支持 `UMF` 和 `CSP`；输入值必须去除首尾空白并统一按大写比较，任务元数据保留规范化后的值。
- **FR-002**：创建巡检包时网元类型必须为必填项；日志补充包不得携带网元类型、省份或运营商元数据。
- **FR-003**：巡检包必须根据上传网元类型启用对应规则集：UMF 启用 UMF 精细目录规则，CSP 仅启用 CSP 告警及跨网元通用告警规则。
- **FR-004**：跨网元告警规则必须先于网元非告警规则和 `0/` 忽略规则执行；UMF 包中出现 CSP 告警目录时必须照常识别，CSP 包中出现 UMF 告警目录时也必须照常识别。
- **FR-005**：CSP 非告警内容不得进入工作分类现场；UMF 中未命中明确路线的普通文件必须进入 `other/` 并保留场景相对路径。

#### 基于真实路径的分类

- **FR-006**：分类必须只使用归一化后的真实来源路径、明确目录后缀、明确文件名模式和显式动作，不得使用文件内容嗅探、成员名猜测、通用扩展名兜底或路径中任意出现 `alarm/告警` 的宽泛匹配。
- **FR-007**：来源路径必须以 `/` 归一化，目录段匹配必须大小写不敏感，外层包装目录不得成为稳定匹配条件，也不得进入最终目标路径。
- **FR-008**：每条分类规则必须声明适用网元集、来源路线、优先级、动作、业务分类和目标路径模板；多个来源路线可以声明相同业务分类和目标根目录。
- **FR-009**：同一来源路径命中多条规则时，必须按声明的确定优先级选择唯一路线；如配置存在同优先级冲突，配置校验必须失败。
- **FR-010**：未命中任何明确路线的 UMF 普通文件必须按场景相对路径进入 `other/`；未明确声明展开的压缩包必须保留原文件名进入 `other/<场景相对路径>`，不得自动展开。
- **FR-011**：系统必须支持不同来源目录映射到同一物理目标根目录，并保持证据可通过路线和原路径追溯；目标重名时不得静默覆盖。

#### UMF 精细分类映射

- **FR-012**：`Basic Information About the UMF/` 下的文件必须进入 `basic/`，业务分类为 `config`，目标保留其相对于该来源目录的路径。
- **FR-013**：场景根级 `collectandcheck.ini` 未命中精细路线时必须进入 `other/collectandcheck.ini`。
- **FR-014**：`Debugging Commands/` 下的文件必须进入 `debug/`，业务分类为 `status`。
- **FR-015**：`Equipment Status/`、`MESH Information (Problem)/` 和 `System Resources/` 下的文件必须进入 `status/`，业务分类均为 `status`。
- **FR-016**：`Operation Logs/operationlog_history_*.csv` 必须进入 `operation-log/`，业务分类为 `operation`。
- **FR-017**：`MML Configurations/EXP MML.txt` 必须进入 `mml/`；`MML Configurations/EXPMML_*.zip` 必须展开，其成员进入 `mml/<成员相对路径>`；两类文件业务分类均为 `config`。
- **FR-018**：`Performance Measurement Results/PerfResult_*.zip` 必须展开，其全部成员进入 `kpi/<成员相对路径>`，业务分类为 `kpi`，不得再按成员扩展名或成员名称重新分类。
- **FR-019**：`MESH Application Metrics/CollectExport*.zip` 必须展开到 `other/MESH Application Metrics/<压缩包名不含扩展名>/<成员相对路径>`，业务分类为 `other`，不得进入 `kpi/`。
- **FR-020**：`CHR Information/ServiceLogs_*.zip` 必须只选择成员中的 `*.bil.gz`，并全部解压为 `.bil` 后进入 `chr/<去除 .gz 的成员相对路径>`，业务分类为 `chr`；其他成员不得进入工作现场，其中 `LocalLogReport.csv` 必须明确排除并记录忽略原因。
- **FR-021**：`Host Debugging Logs/DEBUG.tar.gz` 必须展开到 `host-debug/`，`Host System Logs/OS.tar.gz` 必须展开到 `host-system/`，业务分类均为 `log`；归档成员中的 `.log.gz` 必须解压为 `.log`。
- **FR-022**：`Service Logs (Problem)/ServiceLogs_*.zip` 必须按 FR-029 至 FR-032 做选择性日志保留。

#### 告警分类

- **FR-023**：任意前缀下出现完整目录段 `Alarm Information/` 时，其后缀必须整体作为 UMF 告警路线。
- **FR-024**：任意前缀下出现完整目录段 `Alarm Data/` 时，其后缀必须整体作为 CSP 告警路线；匹配不得依赖 `Problems`、设备名、`0` 或其他前置目录。
- **FR-025**：告警路线下的普通文件和压缩包必须递归展开或解压，成员统一进入 `alarm/<归档内部相对路径>`，去掉告警来源目录层和归档外层，业务分类为 `alarm`。
- **FR-026**：告警路线优先级必须高于 `0/` 忽略规则；非告警 `0/` 内容继续忽略，告警 `0/` 内容必须处理。
- **FR-027**：告警分类不得依据文件大小或记录数筛选；0 字节、仅表头、零记录和含记录的告警文件均必须落位，后续解析再区分空文件和零告警记录。
- **FR-028**：ZIP、TAR、TAR.GZ 和单文件 GZIP 在告警路线内必须递归安全展开；损坏或预算不足的单个归档不得阻止其他告警文件落位。

#### Service Logs 业务主日志

- **FR-029**：Service Logs 归档只保留以下业务主日志：`UMFAcc.log`、`UMFAcc_*.log.gz`、`UmfService.log`、`UmfService_*.log.gz`、`CacheService.log`、`ResourceManageService.log`。
- **FR-030**：保留文件必须去掉 `Service Logs (Problem)/ServiceLogs_*.zip` 外层，按 `logs/<服务>/<原始节点与pod相对路径>/<日志名>` 落位；选中 `.log.gz` 必须解压为同名 `.log`。
- **FR-031**：`RScheck/`、`rscheck*.gz`、`dblog.tar.gz`、`UFP_*.log`、`UFP_MSS_2_0.zip`、`monitor_detect.log`、`UmfService_monitor.log`、`start/proxy` 日志、`bbox*.dat.txt` 和 `LocalLogReport.csv` 必须排除出日志工作现场并记录未选原因。
- **FR-032**：真实基准 UMF Service Logs 归档必须稳定得到 98 个业务主日志，其中 85 个由 `.log.gz` 解压得到，13 个为原始 `.log`；不得保留额外日志。

#### 按需展开与动作

- **FR-033**：只有配置明确声明 `展开` 或 `解压` 的归档或 GZIP 才能产生工作分类文件；未知归档必须原样保留。
- **FR-034**：归档路线命中的后续嵌套归档默认继承该路线的展开语义；告警路线必须递归处理所有受支持归档格式。
- **FR-035**：归档展开必须使用安全路径、链接检查、目标边界、成员数量/大小/深度和资源预算防护；所有失败必须记录来源、目标、错误码和原因。
- **FR-036**：分类落位不得覆盖已有文件；目标冲突时必须使用稳定、可追溯且不损失证据的解决方式，并在审计记录中保留原始目标和实际目标。

#### 配置、快照与重建

- **FR-037**：分类规则必须外部可配置，支持声明来源目录、文件名模式、优先级、适用网元、动作、业务分类和目标模板，不要求为每次目录调整修改巡检代码。
- **FR-038**：分类配置必须在使用前完整校验；空配置、未知动作、未定义目标、无合法业务分类、同优先级冲突或不可达默认行为必须使任务以明确配置错误失败，不得部分执行。
- **FR-039**：分类配置必须有稳定语义指纹；注释、空白和非语义排版变化不得改变指纹，路径、模式、优先级、动作、业务分类或目标模板变化必须改变指纹。
- **FR-040**：任务分类快照必须至少包含分类配置指纹、上传网元类型、规则集、解压策略和路径限制上下文。
- **FR-041**：复用分类现场前必须同时校验主包校验和、证据现场、分类快照和配置指纹；任一不一致时必须从 `.main/` 证据现场重建分类工作目录与分类清单。
- **FR-042**：证据现场缺失或损坏时，系统必须从原始上传包重新建立证据现场，并复核主包校验和；重建过程不得修改、移动、删除、重命名或覆盖真实上传包。
- **FR-043**：重建必须清除旧分类工作目录和旧分类清单，防止历史文件残留；不得删除证据现场、原始包、规则结果或与本次分类无关的任务数据。

#### 审计与文件清单

- **FR-044**：分类审计记录必须包含来源相对路径、命中路线、网元类型、业务分类、原始目标、实际目标、动作、状态、失败原因和配置指纹。
- **FR-045**：分类日志必须提供按路线、业务分类、动作和状态汇总的计数，并列出未命中、忽略、冲突和失败项，使运维人员能定位规则为何未执行。
- **FR-046**：巡检文件清单必须只包含审计状态为成功落位的文件，路径相对于任务目录并以 `/` 归一化；不得再固定扫描全部物理分类目录来推断可巡检文件。
- **FR-047**：分类清单必须排除证据现场、分类配置、分类审计文件、prepared 数据、规则结果、报告、任务元数据和执行日志。
- **FR-048**：普通巡检规则没有匹配任何分类清单文件时，必须返回 `skip` 和非空 `skip_reason`。
- **FR-049**：分类审计中的业务分类属于本功能内部审计语义，不得为 `status`、`operation`、`chr` 等业务分类扩展或重定义公共巡检规则分类契约。

#### 兼容与安全

- **FR-050**：日志补充包不得要求或接受网元类型、省份和运营商元数据，也不得触发 UMF/CSP 精细分类或台账匹配。
- **FR-051**：本地模式与在线模式必须对同一包、同一网元类型和同一配置产生相同的分类目标、业务分类、审计状态和巡检文件清单。
- **FR-052**：安全解压必须拒绝路径穿越、绝对路径、链接逃逸、越界目标、非法重复路径和超限资源，不得因单个成员失败中断整个任务。
- **FR-053**：主包无法安全解压时任务必须失败且不得进入 prepare 或 inspect；子包或单个 GZIP 失败时任务继续处理其余合法文件。
- **FR-054**：分类动作必须幂等；同一包、同一网元类型和同一配置重复执行不得产生重复目标、随机路径或不同业务分类。

### 关键实体

- **巡检包**：用户上传的只读归档，具有唯一包名、校验和、包类型和网元类型；一个包对应一个任务。
- **网元类型**：巡检包的必需元数据，本阶段取值为 UMF 或 CSP，用于选择精细分类规则集和台账匹配。
- **分类路线**：从真实来源路径到业务分类和物理目标的规则，包含适用网元、来源目录后缀、文件名模式、优先级、动作和目标模板。
- **分类配置**：对分类路线的完整声明，具有语义版本或稳定指纹；配置变化会使旧分类现场失效。
- **分类审计项**：单个来源文件或归档动作的决策记录，连接来源、路线、业务分类、目标、动作、状态和失败原因。
- **分类清单**：所有成功落位文件的目标相对路径集合，是巡检规则唯一可见的工作文件范围。
- **分类快照**：配置指纹、网元类型、规则集、解压策略和路径限制上下文的组合，用于判断分类现场能否复用。
- **证据现场**：直接从主包安全展开得到的只读原始目录，是配置变化后重建分类现场的权威来源。

## 假设

- “0 告警”指零条告警记录，不是名为 `0/` 的目录；两者在审计和后续展示中使用不同名称与语义。
- `Service Logs (Problem)/ServiceLogs_*.zip` 是 UMF 当前业务日志入口；其他服务日志归档只有在后续配置明确声明后才进入 `logs/`。
- 未命中明确路线的压缩包默认原样保留到 `other/<场景相对路径>`，因为本功能要求“按需展开”，不得对所有归档做成员嗅探。
- CSP 本阶段只补告警，非告警内容不纳入本次工作分类；UMF 非告警内容按本规格精细分类。
- 告警文件的有效性、记录数和表头校验由后续告警解析能力负责；分类阶段只保证证据不丢失并发生正确落位。
- 业务分类 `status`、`operation`、`chr` 等只用于分类审计和后续规则寻址，不等同于现有公共 `RuleCategory` 枚举。
- 分类配置为部署侧静态配置，本阶段不增加在线编辑、热加载或任务级覆盖入口。
- 分类配置指纹采用规范化有效配置计算；具体规范化形式在实现计划中确定，但必须满足 FR-039 的可观察行为。
- UMF 和 CSP 的业务分类差异由上传网元类型决定；跨网元告警识别是例外，始终优先执行。
- 本功能不恢复已下线的非 KPI 普通巡检规则，也不因新增多级目录而修改既有规则结果契约。
- 真实基准包只作为只读验收输入，不复制、移动或提交到 Git；真实包派生输出必须位于隔离的临时目录或已忽略的任务目录。

## 范围外

- 不新增 CSP 非告警内容的精细分类。
- 不新增在线分类配置编辑页面、配置热加载或按任务覆盖配置。
- 不依据文件内容、CSV 表头或数据行判断告警是否有效。
- 不恢复日志、告警、配置、状态、资源或 CHR 的非 KPI 普通巡检规则。
- 不改变既有 KPI 规则的判定逻辑和 `rule_version`；如实现中发现必须改变规则可见输入，应在计划与任务中单独评估。
- 不修改、移动、提交或压缩真实上传包。
